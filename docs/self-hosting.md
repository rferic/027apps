# Self-hosting 027Apps

This guide walks you through standing up your own 027Apps instance from an empty set of
accounts to a working preview deployment. It is the **public, step-by-step path**; the internal
runbook with recovery scenarios and secret inventory is [`docs/infrastructure.md`](infrastructure.md)
(in Spanish), and the CI/CD details are in [`docs/flows/cicd.md`](flows/cicd.md).

> **Security rules for the whole guide**
>
> - Secret values never go into git, logs, issues, or chat. Commands that need a secret read it
>   from `stdin` or from your password manager.
> - Every variable below is listed by **name only**. You paste the value in the dashboard or in
>   your local `.env.local`, which is git-ignored.
> - Use 2FA on GitHub, Supabase, Vercel, Firebase and your email provider.
> - If an AI assistant is guiding you (see [AI-assisted setup](#ai-assisted-setup)), it must not
>   ask you to paste secrets into the conversation.

## What you are building

| Piece | Purpose | Free plan |
|---|---|---|
| **Supabase** (cloud) | Postgres, Auth, Storage, Realtime | Free: 500 MB, no backups, pauses when idle |
| **Supabase** (local) | Development database and Auth for TDD | Docker, no cost |
| **Vercel** | Admin panel (`apps/admin`) and `/api/v1` | Hobby |
| **GitHub** | Code, CI, releases | Free (public repo: Actions minutes free) |
| **Resend** (or Brevo) | Transactional email for invitations and password resets | Free: ~100/day |
| **Firebase** (optional) | Push notifications via FCM | Free |
| **Cloudflare R2 / Backblaze B2** | Encrypted database backups | R2: 10 GB free |

Architecture in one line: **Next.js admin on Vercel → Supabase (Postgres/Auth/Storage)**, Android
app talking to the same API, optional FCM for push, optional Resend for email.

## Prerequisites

- Node.js 26+ and pnpm 10+
- Docker (for local Supabase)
- Git and the GitHub CLI (`gh`), authenticated
- A JDK with `keytool` (only if you will publish Android releases)
- Accounts: GitHub, Supabase, Vercel; optional Firebase and an email provider

## Phase 0 — Run it locally

```bash
git clone https://github.com/<you>/027apps.git
cd 027apps
pnpm install
supabase start          # local Postgres, Auth, Storage, Mailpit
```

Create `apps/admin/.env.local` from `apps/admin/.env.example` and fill the **local** demo keys
that `supabase start` prints. Then:

```bash
pnpm --filter admin dev
curl -s http://localhost:3000/api/health   # {"status":"ok"}
```

**Verify:** `/api/health` returns `200 ok`; Mailpit at `http://127.0.0.1:54324` shows auth emails.

## Phase 1 — Supabase cloud (development instance)

1. Create a project named `027apps-dev` in the Supabase dashboard (choose the region closest to
   your users; the reference instance uses `eu-west`).
2. Save the database password in your password manager. It is shown only once.
3. Copy the **Project URL**, the **anon/publishable key** and the **service_role/secret key** from
   *Project Settings → API*. The service role key bypasses RLS: treat it as a secret.
4. Link the repo and push the schema:

```bash
supabase link --project-ref <your-project-ref>
supabase db push
```

5. In *Authentication → URL Configuration*, set the Site URL to your preview/production domain
   once you have it. In *Authentication → SMTP* you will configure email in Phase 4.

**Verify:** `curl -s https://<ref>.supabase.co/auth/v1/health` returns `401` with
`"No API key found in request"` — the project exists and requires an API key. The schema tables
appear in *Table Editor* after `db push`.

## Phase 2 — Environment variables and the master key

The admin needs these variables. Use **Preview** scope first; add **Production** scope only when
you activate production (see [`docs/infrastructure.md` §9](infrastructure.md#9-producción--activación-sprint-13)).

| Variable | Scope | Type | Where the value comes from |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Preview | Plain | Supabase → Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Preview | Plain | Supabase → anon/publishable key |
| `SUPABASE_SERVICE_ROLE_KEY` | Preview | **Sensitive** | Supabase → service_role/secret key |
| `SETTINGS_ENCRYPTION_KEY` | Preview | **Sensitive** | Generated by you (32 random bytes, base64) |

Generate the master key locally and keep a copy in your password manager **separate from the
database backups**:

```bash
openssl rand -base64 32 > ~/.config/027apps/master-key   # chmod 600
```

Without this key, secrets stored in `settings.value_encrypted` are unrecoverable. A backup plus
the key equals plaintext, so never store them together.

**Verify:** the four names exist in Vercel (*Settings → Environment Variables*) with the right
scope. No value appears in git (`git status` must be clean of `.env*`).

## Phase 3 — Vercel (previews)

1. *Add New → Project → Import Git Repository* and pick your fork.
2. **Root Directory:** `apps/admin`. Enable **Include source files outside of the Root
   Directory** (the pnpm workspace needs the root `pnpm-workspace.yaml`).
3. Framework: Next.js (auto-detected).
4. **Production Branch:** `main`. Production is `main`; staging is a long-lived `staging` branch
   assigned to the Preview environment (Hobby has no custom environments). Create `staging` from
   `main`; merges to `staging` deploy staging and only a `staging → main` pull request reaches
   production ([`docs/flows/git.md`](flows/git.md)). Until you activate production (Phase 9), do
   not assign a production domain, so nothing goes live by accident.
5. Add the variables from Phase 2 with **Preview** scope (all branches, including `staging`),
   pointing at your development Supabase project. Add them to **Production** scope, with your
   production project's values, when you activate production.
6. Enable *Deployment Protection → Standard Protection* so previews and `staging` require your
   team login while the production domain stays public. Do not use *All Deployments*.
7. Optionally assign a custom domain. Reserve the app domain for production and use a dedicated
   subdomain for email (Phase 4); never use the same subdomain for both.

**Verify:** open a PR and wait for the Vercel check. The preview URL responds `/api/health` with
`200 ok` when you are logged in to the team. A push to `staging` deploys staging the same way.

## Phase 4 — Transactional email (Resend or Brevo)

Auth needs a custom SMTP provider; the built-in sender is rate-limited and not for production.

1. Create a free account at [Resend](https://resend.com) (or Brevo).
2. Add a **dedicated subdomain** for email, e.g. `mail.example.com`, and create the DNS records
   the provider shows (DKIM, SPF, return-path). If your DNS lives in Vercel, add them there.
3. Wait for the domain to show **Verified**.
4. In Supabase *Authentication → SMTP*, configure:

| Field | Resend value |
|---|---|
| Host | `smtp.resend.com` |
| Port | `465` (SSL) or `587` (TLS) |
| Username | `resend` |
| Password | your Resend API key (secret) |
| Sender email | `no-reply@mail.example.com` |
| Sender name | your app name |

5. After enabling custom SMTP, Supabase limits Auth to **30 messages/hour** by default; raise it
   in *Authentication → Rate Limits* if you need more.

**Verify:** invite your own email from *Authentication → Users → Invite* and confirm the message
arrives (check spam the first time). Then test a password reset end to end.

## Phase 5 — GitHub protections and release environment

Do this **before** uploading any signing key. The order is deliberate: secrets must not exist
before the protections that keep them safe.

1. **Protect `staging` and `main`** with a ruleset each: require a pull request, the CI checks
   (`admin`, `android`, `supabase`, `guard-secrets`, `commitlint`, `ai-docs`) and no force
   pushes.
2. **Protect tags `v*`** with a ruleset that only the admin can create.
3. **Create an Environment named `release`** with yourself as required reviewer. Release secrets
   are only exposed to jobs triggered by `v*` tags.
4. Add a `CODEOWNERS` file so workflow and secret-related paths require your review.
5. Keep the `guard-secrets` workflow green: it blocks commits containing keys, keystores or
   `google-services.json`.

**Verify:** a PR without checks cannot merge; a tag created by a non-admin is rejected; the
`release` environment lists you as reviewer.

## Phase 6 — Android release keystore (only if you publish APKs)

```bash
keytool -genkeypair -v \
  -keystore 027apps-release.jks \
  -alias 027apps \
  -keyalg RSA -keysize 4096 \
  -validity 10000
```

`keytool` asks for the password and certificate data. Modern `keytool` creates a **PKCS12**
keystore, which uses **one password for both the store and the key**.

1. Copy the `.jks` file, the password and the alias to your password manager. Without them you
   can never publish a signed update again.
2. Upload the four secrets to the `release` environment, reading values from local files:

```bash
gh secret set ANDROID_KEYSTORE_BASE64 --env release < <(base64 < 027apps-release.jks)
gh secret set ANDROID_KEYSTORE_PASSWORD --env release   # prompts on stdin
gh secret set ANDROID_KEY_ALIAS --env release --body 027apps
gh secret set ANDROID_KEY_PASSWORD --env release        # prompts on stdin
```

3. **Only after confirming the backup**, delete the local `.jks`.
4. Publish a test tag (`v0.1.0`) and confirm the Release contains a signed APK that installs.

**Verify:** `gh secret list --env release` shows the four names; the tag run produces a signed
APK; the keystore is not in git history.

## Phase 7 — Firebase / FCM (optional push)

1. Create a free Firebase project and register an Android app with your package name
   (`com.rferic.zero27apps` in the reference instance).
2. Copy the **public** values (`project_id`, `app_id`, `api_key`, `sender_id`) into the admin
   settings when the Core panel exists.
3. Generate a **service account** JSON for server-side sends. Store it in your password manager;
   it goes encrypted into `settings`, never into git.
4. Restrict the API key in Google Cloud: Android app + package + release SHA-1, and only the APIs
   you use.

**Verify:** a test notification reaches the device with the app closed. Without FCM the app still
works (realtime + inbox fallback).

## Phase 8 — Backups

The free Supabase plan has no backups. Set up your own from day one.

1. Create a private bucket in Cloudflare R2 or Backblaze B2 and an S3 token scoped to that bucket.
2. Generate `RESTIC_PASSWORD` and store it in your password manager **and on paper**:
   `openssl rand -base64 48`.
3. Copy the **session pooler** connection string (IPv4) from Supabase and keep the database
   password.
4. Upload the five secrets (`SUPABASE_DB_URL`, `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`,
   `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`; plus `BACKUP_S3_REGION` if not R2) as described in
   [`docs/infrastructure.md` §4](infrastructure.md#4-backups).
5. Run *Actions → Backup → Run workflow* and confirm a snapshot lands in the bucket.
6. Do a restore drill against a clean Postgres before trusting the backup.

**Verify:** the workflow is green, `restic snapshots` lists the snapshot, and the drill restores
`public` with verifiable rows. Details: [`docs/infrastructure.md` §5–6](infrastructure.md).

## Phase 9 — Activate production

Follow the checklist in [`docs/infrastructure.md` §9](infrastructure.md#9-producción--activación-sprint-13):
create `027apps-prod`, fill Production env vars, set the production branch to `main` (and delete
any placeholder `production` branch), assign the domain, configure SMTP, apply migrations, take a
backup and verify health, invitations and password resets.

## Final verification checklist

- [ ] Local stack: `/api/health` → `200 ok`
- [ ] Supabase cloud: schema pushed, Auth responds `401` without a key
- [ ] Vercel: PR preview green and protected; `staging` deploys; production branch is `main`
- [ ] Email: domain verified; invitation and reset received
- [ ] GitHub: `staging`, `main` and `v*` protected; `release` environment with reviewer; `guard-secrets` green
- [ ] Keystore backed up and secrets uploaded (if publishing APKs)
- [ ] FCM working or explicitly skipped
- [ ] Backup run green and restore drill done
- [ ] No secret in git, logs or chat

## Troubleshooting and limits

| Symptom | Cause / fix |
|---|---|
| Vercel rejects the production branch | The branch does not exist in GitHub; production branch is `main`, create `staging` from it |
| Preview URL asks for login | Vercel Authentication is on; that is intended. Log in with the team account |
| Supabase project paused | Free tier pauses idle projects; restore it from the dashboard |
| Auth emails not delivered | Domain not verified, wrong SMTP port, or rate limit hit; check Resend logs |
| `release` job fails | Missing keystore secrets, or the tag was not created by the admin |
| Backup workflow green but no snapshot | Secrets missing: the workflow skips steps by design |
