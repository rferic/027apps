diseña aquí (F1) y se implementa en la tarea 04.

[README del sprint](../../tasks/sprint-15-app-y-finanzas/README.md).

## Parte C — Dominio (TDD, sin red ni base)

> Orden obligatorio: test rojo → implementación → verde → refactor. Cada caso de la spec §6 es
> un test con nombre propio.

### C1. Dinero y fechas

- [ ] `Money` en enteros de céntimos: suma, resta, comparación y formato; ningún `float`.
- [ ] Fecha de calendario `YYYY-MM-DD` sin conversión de zona.

### C2. Reparto igual con participantes

- [ ] `k=1`, `k=n`, resto `total % k != 0`: las `rem` primeras participaciones por id reciben
      un céntimo más; la suma siempre es el total.
- [ ] Subconjunto de 3 de 5; pagador dentro y fuera del reparto.
- [ ] Cero participantes → error `no_participants`; participantes `invited`/`left` → error.

### C3. Reparto exacto

- [ ] Suma distinta del total → error con detalle por miembro.
- [ ] Un miembro no seleccionado en `shares` → error.
- [ ] Importes a cero permitidos; negativos no.

### C4. Balances

- [ ] Fórmula única sobre `movements` no borrados; suma cero con gastos, pagos y miembros que
      salen.
- [ ] Un pago es un movimiento con una sola participación (receptor ≠ pagador) y mueve el saldo
      igual que un gasto.
- [ ] Un gasto con una sola participación (compra solo para Luis) **no** se confunde con un
      pago: `kind` manda.

### C5. Liquidación exacta

- [ ] Implementar la búsqueda con retroceso de la spec §6.5, orden canónico por `member_id`.
- [ ] **Oráculo de fuerza bruta** para `m ≤ 6`: el resultado coincide y nunca es menor.
- [ ] Determinismo con saldos repetidos y con orden de entrada barajado.
- [ ] Conservación: cada deudor paga su deuda y cada acreedor cobra su crédito.
- [ ] Tope: `m = 13` con tope 12 → voraz y aviso; con tope 20 → exacto.
- [ ] Sin dependencias externas; complejidad documentada en el módulo.

### C6. Reglas de movimiento

- [ ] Editar/borrar: autor o creador; otro miembro recibe `forbidden`.
- [ ] Baja lógica: el movimiento sale del historial y de balances; la fila sigue.
- [ ] Borrar un gasto con un pago posterior no borra el pago; los balances se recalculan.
- [ ] Un `settlement` con más de una participación o con pagador = receptor → error.

### C7. Ciclo de vida

- [ ] Invitar/aceptar/rechazar; echar con y sin saldo; bloquear impide reinvitar; salir con
      saldo cero y con saldo → `balance_not_zero`.
- [ ] Purga de usuario con historial: el miembro pasa a ficticio, conserva nombre e importes.

## Parte D — API

> Todo borde con zod, envelope ADR 0007, idempotencia en escrituras y rate limit. Los tests de
> API viven junto al caso de uso y en `db-tests` cuando tocan RLS.

### D1. Grupos

- [ ] `GET /owe-no/groups` (paginado), `POST`, `GET /{id}`, `PATCH /{id}` (nombre, moneda,
      archivar). El creador es miembro `active` al crear.
- [ ] Moneda del grupo validada; cambiar de moneda con movimientos → error explicado.

### D2. Miembros e invitaciones

- [ ] Listar/invitar; aceptar/rechazar; echar; bloquear; enlazar ficticio (admin); salir.
- [ ] `403` para quien no es creador; `404` uniforme para otro grupo.
- [ ] Invitar a un bloqueado → `validation_failed` con `code: blocked`.

### D3. Movimientos

- [ ] `GET /movements` con filtros (`from`, `to`, `category_id`, `member_id`, `kind`) y paginación.
- [ ] `POST /movements` (`expense` y `settlement`) con `Idempotency-Key`.
- [ ] `GET /movements/{id}` con participaciones.
- [ ] `PATCH` y `DELETE` (baja lógica) solo autor o creador.
- [ ] Devolver balances recalculados en cada escritura.

### D4. Balances y plan de liquidación

- [ ] `GET /balances`: saldos, `settlement` con `exact`, `limit` y `transfers`, y `pending` de
      quien salió (solo creador).
- [ ] Leer el tope del setting del módulo, no de una constante.

### D5. Categorías

- [ ] Listar y crear por grupo; borrar una categoría no borra movimientos (`on delete set null`).

### D6. Importador de Splitwise (puerta: CSV redactado)

- [ ] Parser por **impacto por persona**, no por etiqueta; pagador y participaciones derivados.
- [ ] Fechas ISO; decimales con `.` o `,` sin ambigüedad; paréntesis negativos; nunca `float`.
- [ ] **Multi-divisa → rechazo entero** con `code: multi_currency` y lista de divisas.
- [ ] Pagos detectados por marcador → `kind: settlement`; si no hay marcador, entran como gasto
      de dos personas (los balances son idénticos).
- [ ] Autoenlace por **nombre exacto y único**; selector de usuarios activos; crear ficticio;
      fusión de identidades; invitación a registrados que no son miembros.
- [ ] Límite 2 MB / 5.000 filas; celdas con `=`, `+`, `-`, `@` se guardan como texto y se
      escapan al mostrar.
- [ ] `preview` sin escrituras; `commit` en una transacción; deduplicación por hash de fila y
      `confirm_duplicates`.
- [ ] Tests con el **CSV redactado** como fixture; errores con número de línea.

### D7. Usuarios enlazables e historial de importaciones

- [ ] `GET /linkable-users` (id + nombre, sin email ni rol) solo para el creador.
- [ ] `GET /imports` con recuentos y resultado.

### D8. Eventos, push e idempotencia

- [ ] Emitir en la misma transacción del caso de uso (`enqueueEvent`), nunca después.
- [ ] Excluir al **autor** de los tokens de push (tarea 02).
- [ ] Rate limit por usuario y por grupo; clave de idempotencia repetida devuelve el mismo
      recurso.

### D9. OpenAPI y documentación

- [ ] Registrar las operaciones en `packages/core/src/openapi/registry.ts` y regenerar
      `docs/api/openapi.json`; `pnpm check:openapi` en verde.
- [ ] `docs/api/README.md` con los endpoints del módulo y los códigos de error propios.
