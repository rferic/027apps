## 1. Objetivo

Que la familia use iPhone con una app **que se sienta nativa** (SwiftUI, no un port envuelto),
sin que el propietario tenga que revisar código Swift ni probar cada pantalla, y sin que la app
iOS se quede atrás cada vez que evoluciona Android.

La decisión de fondo: **el conocimiento se exporta, la implementación es nativa**. No se comparte
código con Android; se comparte un **contrato ejecutable** que ambas apps deben cumplir, y el CI
falla cuando una se desvía.

El propietario ya ha verificado en Android lo que es portable a nivel de producto: endpoints,
reglas de negocio, jerarquía de pantallas, textos y decisiones de UX. Esa verificación **no se
repite**. Lo que sí hay que verificar en iOS es la ejecución nativa y las integraciones propias de
la plataforma.

## 2. Alcance

### 2.1 Dentro

- App iOS nativa con paridad funcional del conjunto Android congelado en el arranque (§12),
  **incluyendo lo que esté en desarrollo en ese momento** (hoy, sprint 18 y lo que se abra antes
  del arranque).
- `spec/mobile/` como fuente de verdad del comportamiento, con fixtures, escenarios y contratos de
  pantalla ejecutados por los dos test suites.
- Generadores: DTOs Kotlin/Swift desde `/api/v1/openapi.json`, textos de los 9 idiomas, tokens de
  diseño.
- Divergencias de plataforma declaradas y acotadas (§8): widget, actualización, deep links, ATS,
  push, Keychain.
- CI con job `ios`, matriz de paridad con check mecánico, release a TestFlight por API.
- Excepción de verificación humana documentada (§7) y su reflejo en
  [definition of done](../../conventions/definition-of-done.md).

### 2.2 Fuera

- Compose Multiplatform, Flutter, React Native o cualquier UI no nativa.
- Kotlin Multiplatform: no se introduce Kotlin/Native en el build de Xcode (§3).
- Auto-actualización de la app: iOS no lo permite; se sustituye por aviso y enlace a TestFlight.
- Publicación en App Store abierta al público. Primera entrega por TestFlight; la decisión de
  publicar se toma después, sin cambiar arquitectura.
- iPad, watchOS, visionOS y extensiones no listadas en §10.
- Rediseñar nada: la jerarquía visual es la de Android, adaptada a las convenciones de iOS.

## 3. Stack y por qué

| Pieza | Elección | Motivo |
|---|---|---|
| Lenguaje | **Swift 6.4** | Concurrency estricta, `async/await`, actores; idiomático y estable |
| UI | **SwiftUI** | Es lo que da la sensación nativa; diseño vigente *Liquid Glass* (iOS 26+) |
| Toolchain | **Xcode 27** (SDK iOS 27) | Versión vigente en 2026-11 |
| Tests | **Swift Testing** + XCTest para UI | `@Test`/`#expect` para escenarios; XCUITest para humo |
| Módulos | **SwiftPM** | Equivalente a módulos Gradle; cachea y separa capas |
| Red/JSON | `URLSession` + `Codable` | Sin dependencias externas en la capa de red |
| Distribución | TestFlight (App Store Connect API) | La familia prueba sin el propietario |

**Por qué no KMP.** Se midió el código duplicable: las reglas de negocio reales que viven en la app
son ~900–1.200 líneas (formato de importes, `parseMinor`, `equalShare`, expiraciones, normalización
de instancia, política de actualización, textos de push, parsers de enlaces) más ~1.100 de máquina
de estados de flujos. El resto es UI (≈5.500), datos generables (i18n 3.528, changelog 424, DTOs
≈1.020) y plataforma. Con ese volumen, la especificación ejecutable es más simple que meter
Kotlin/Native en Xcode y no obliga a que un experto en Kotlin mantenga la app iOS. Si la lógica
duplicable creciera por encima de ~3.000 líneas, esta decisión se revisa con un ADR.

**Por qué no se genera Swift desde Kotlin.** Un transpilador produce Swift no idiomático: es
exactamente lo que rompe "se siente nativa" y lo que ningún revisor puede mantener.

## 4. Arquitectura de tres capas

| Capa | Dueño único | Qué contiene | Cómo llega a iOS |
|---|---|---|---|
| **1. Regla de negocio** | El Core (`/api/v1`) | Saldos, reparto, cuotas, permisos, expiraciones, settlement, summary | La app solo pinta; cero duplicación |
| **2. Comportamiento de app** | `spec/mobile/` | Fixtures de API, escenarios de reglas, contratos de pantalla | Escenarios ejecutados por Kotlin **y** Swift |
| **3. UI y plataforma** | Cada plataforma | Compose / SwiftUI, widgets, push, keychain, deep links | Nativo, sin intentar compartir |

Regla dura que se añade a `AGENTS.md` al aprobar: **ninguna regla de app se implementa sin su
escenario en `spec/mobile/`**. Sin escenario no es contrato y puede divergir en silencio.

Corolario de la capa 1: si una regla puede calcularla el Core, la calcula el Core. La
previsualización local (por ejemplo `equalShare` en el formulario) se mantiene solo como
anticipación visual y su resultado debe coincidir con la respuesta del servidor en los escenarios.

## 5. `spec/mobile/` — formato

```
spec/mobile/
  fixtures/            # respuestas reales de /api/v1, capturadas (nunca inventadas)
    me.json
    dashboard.json
    owe-groups.json
    owe-summary.json
    owe-settlement.json
    invitation-preview.json
    module-list.json
  scenarios/           # reglas y flujos como datos
    owe-parse-amount.yaml
    owe-equal-share.yaml
    owe-format.yaml
    server-url.yaml
    instance-picker.yaml
    invite-expiry.yaml
    push-text.yaml
    session-refresh.yaml
    update-policy.yaml
    flow-invitation-redeem.yaml
    flow-device-migration.yaml
  screens.yaml         # estados y acciones de cada pantalla
  i18n/
    *.json             # 9 idiomas, origen de Kotlin y de .xcstrings
  tokens.json          # origen de Tokens.kt y de los tokens Swift
```

### 5.1 Escenario de regla

```yaml
id: owe.parse-amount
desc: Importes con coma o punto; se rechaza lo ambiguo y el cero.
cases:
  - { input: "12,34", expect: { minor: 1234 } }
  - { input: "12.34", expect: { minor: 1234 } }
  - { input: "12",    expect: { minor: 1200 } }
  - { input: "12,345", expect: { minor: null } }
  - { input: "0",     expect: { minor: null } }
  - { input: "abc",   expect: { minor: null } }
```

Cada suite (Kotlin y Swift) tiene un lector genérico de escenarios. **No hay dos listas de asserts**:
hay un fichero y dos lectores. Añadir un caso y no implementarlo en iOS pone rojo el job `ios`.

### 5.2 Contrato de pantalla

```yaml
id: screen.owe.group
states: [loading, ready, empty, error]
actions: [create-movement, edit-movement, delete-movement, filter-member, open-settlement]
input: [groupId]
```

`screens.yaml` es la lista completa. Un check compara los identificadores declarados con los que
cada app registra en una tabla propia (una constante por plataforma) y falla si falta alguno. No
verifica gestos ni navegación real: eso son las puertas humanas de §7.

### 5.3 Fixtures

Se capturan de una instancia real (local o staging) y se versionan sin datos personales: nombres
ficticios, importes inocuos, tokens caducados. La captura se hace con un script
(`pnpm spec:capture`) contra el stack local, nunca a mano, para que se puedan refrescar cuando
cambie un DTO. Un fixture con un campo nuevo y un DTO sin actualizar es un fallo de test, que es lo
que queremos.

## 6. Propagación de un cambio Android → iOS

Todo cambio de la app cae en uno de tres casos, y el primero es el que hay que buscar siempre:

| Caso | Qué se toca | Qué pasa en iOS | Tu intervención |
|---|---|---|---|
| **A. Regla de negocio** | Core: ruta, zod, migración | Nada. La app pinta lo que recibe | Ninguna |
| **B. Comportamiento existente cambia** (nuevo estado, nueva validación, nuevo texto, nuevo campo) | `spec/mobile/` (escenario/fixture/pantalla) + Android | El job `ios` se pone **rojo** hasta que Swift cumple el escenario | Ninguna |
| **C. Capacidad nueva** (pantalla, flujo, módulo) | `docs/ai/parity.md` (fila nueva) + spec móvil si aplica | Fila `ios: pendiente` con dueño y sprint; la release iOS no se bloquea, pero la paridad no está en verde | Ninguna |

El caso B es el que resuelve la pregunta de partida: **no hay que "acordarse de portar"**. El
escenario compartido es el portapapeles; el check es el que se acuerda.

Orden obligatorio en el PR de Android que toca comportamiento:

1. Escenario/fixture en `spec/mobile/` (rojo en ambos suites).
2. Implementación Android (suite Kotlin verde).
3. Implementación iOS en el mismo PR **o** fila de paridad con `ios: pendiente` y sprint asignado,
   si el trabajo iOS va en un PR posterior. El merge a `staging` no exige iOS implementado (la app
   todavía no existe cuando se escriba la primera tanda), pero **sí exige la fila**, y
   `pnpm check:parity` falla si falta.

Cuando la app iOS ya esté publicada en TestFlight, el caso B pasa a exigir las dos implementaciones
en el mismo sprint: es una línea de `AGENTS.md`, no una promesa.

## 7. Verificación: modelo de puertas

Excepción aceptada por el propietario (2026-11-21): **no hay revisión humana de código Swift ni
prueba pantalla a pantalla por su parte**. Se sustituye por tres puertas y por checks mecánicos.

| Puerta | Cuándo | Quién | Coste | Qué valida |
|---|---|---|---|---|
| **G0 — automática** | Cada push | CI | 0 | Build, unit tests, escenarios de `spec/`, XCUITest de humo en simulador, `check:parity`, auditoría de seguridad con checklist iOS |
| **G1 — patrón** | Tras las 2–3 primeras pantallas | El propietario, 30–40 min | 40 min | Tipografía, navegación, hojas, color, densidad, sensación. Si el patrón está bien, las demás lo heredan |
| **G2 — integraciones** | A mitad, con TestFlight operativo | **Tercero con iPhone** (familia), checklist de 10 puntos | 0 para el propietario | Push real, universal links, widget, keychain tras reinstalar, instancia propia |
| **G3 — frontal** | Todo verde en G0 | El propietario, 2–3 h | 2–3 h | Pasada completa con checklist de 15 puntos |

**Por qué G1 existe y no se puede saltar.** Si el patrón visual está mal, no se revisa una pantalla:
se rehacen diez construidas sobre una suposición equivocada, y ese trabajo es en serie. G1 cuesta 40
minutos y es lo único que impide que G3 se convierta en tres días de triaje.

**Lo que G0 no puede cubrir y por eso existe G2** (solo dispositivo real): entrega real de APNs y
token de dispositivo, universal link abierto desde Safari/Mail/WhatsApp, widget en pantalla de
inicio con su presupuesto de refresco, Keychain tras reinstalar, rendimiento y hápticos en hardware.

**Auditoría de seguridad iOS** (obligatoria, agente distinto del autor). Además de la checklist
general de [seguridad](../../conventions/security-checklist.md), para iOS:

- token de sesión solo en Keychain (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`), nunca en
  `UserDefaults`, ni en logs, ni en `print`.
- Enlaces de invitación/unión/traspaso: el token no viaja en la URL que se abre, no se registra y
  no se copia al portapapeles sin caducidad. Antecedente real en Android: fuga del token por deep
  links de unión.
- ATS: excepción de HTTP limitada a hosts privados (RFC 1918 + `localhost`), simétrica con
  `ServerUrl`, y revisada en la App Store submission.
- Sin secretos en el binario: ni claves de servicio, ni endpoints privilegiados.
- `NSUserTrackingUsageDescription` ausente y sin SDKs de terceros que rastreen (la app no los
  necesita).

## 8. Divergencias aceptadas por plataforma

Se declaran aquí una vez y se reflejan en `docs/ai/parity.md`. No son deuda oculta: son decisiones.

| Capacidad | Android | iOS | Motivo |
|---|---|---|---|
| Actualización | APK desde `/api/v1/app/android`, instalación directa | Aviso + enlace a TestFlight | iOS no permite auto-actualizar |
| Widget | Glance + WorkManager, refresco propio | WidgetKit, refresco por el sistema | Sin API equivalente; el widget iOS será menos "fresco" |
| Enlaces | App Links (`assetlinks.json`) + scheme `zero27apps://` | Universal Links (AASA) + scheme `zero27apps://` como reserva | AASA por dominio; en instancias propias el scheme es la reserva fiable |
| Push | FCM | FCM → APNs + `UNNotificationServiceExtension` para el texto localizado | El texto localizado de `PushText` se ejecuta en la extensión |
| Sesión cifrada | Keystore | Keychain | Primitivo distinto, misma semántica |
| Instancias en HTTP local | Permitido en debug | ATS con excepción a hosts privados | Requisito de ATS |
| Cámara / QR | CameraX + ML Kit | `AVCaptureSession` + Vision | Nativo |

## 9. Generación de código

`pnpm gen:mobile` produce, y CI verifica que el resultado está al día (si no, falla):

| Salida | Origen | Destino Android | Destino iOS |
|---|---|---|---|
| DTOs | `/api/v1/openapi.json` | `data/Dtos.kt`, `data/OweDtos.kt` | `CoreAPI/DTOs.swift` (`Codable`) |
| Textos | `spec/mobile/i18n/*.json` | `ui/i18n/Strings.kt` | `Resources/*.xcstrings` |
| Tokens | `spec/mobile/tokens.json` | `ui/theme/Tokens.kt` | `Design/Tokens.swift` |
| Changelog | `apps/android/.../Changelog.kt` (fuente) | — | `Changelog.swift` |

Los textos y tokens no se editan a mano en ninguna de las dos plataformas. 9 idiomas × 2 plataformas
a mano es deuda garantizada; hoy `Strings.kt` tiene 3.528 líneas que solo un generador puede
mantener sincronizadas.

## 10. Integraciones iOS

| Pieza | Implementación | Nota |
|---|---|---|
| Red | `URLSession` + `Codable`, cliente con reintento único tras 401 y refresco de sesión | Calcado del comportamiento de `ApiClient`; escenarios de `session-refresh.yaml` |
| Sesión | Supabase Swift (`supabase-swift`) o OAuth directo si el SDK complica el self-hosting | Decisión en el plan; Keychain para persistir |
| Push | FCM (mismo proyecto que Android) → APNs; `UNUserNotificationCenter`; extensión de servicio para el texto | `PushText` se porta y se verifica con escenarios |
| Deep links | Universal Links + scheme propio de reserva | AASA servida por el Core por dominio |
| Widget | WidgetKit + App Intents, datos desde el mismo endpoint del dashboard | Divergencia de refresco aceptada |
| QR | `AVCaptureSession` + Vision para leer; Core Image para generar | El QR de traspaso y el de invitación comparten generador |

## 11. CI y release

- **Job `ios`** en runner macOS: `xcodebuild test` (unit + escenarios), XCUITest de humo
  (login → home → crear gasto → ver saldo), `pnpm gen:mobile --check`, `pnpm check:parity`.
  Necesario en el PR del sprint junto a `admin` y `android`. Los runners macOS consumen 10×
  minutos: el job se limita a lo imprescindible y cachea SwiftPM.
- **Release**: un tag construye APK (como hoy) y sube a TestFlight con la API de App Store Connect.
  TestFlight interno caduca a los 90 días; el pipeline re-sube. Sin auto-actualización, el aviso de
  versión de iOS solo informa y enlaza.
- **Secretos**: certificado de distribución y clave de API en GitHub Secrets, nunca en el repo. El
  keystore de Android sigue como está. La clave privada de APNs vive en Firebase/App Store Connect,
  no en el binario.

## 12. Baseline de paridad y congelación

La app Android sigue evolucionando mientras se construye iOS. Para que el objetivo no se mueva:

1. **Arranque**: cuando el propietario termine lo que tiene en curso (hoy, sprint 18 y lo que se
   abra antes), se mergea a `staging` y se etiqueta mentalmente como **baseline**. `docs/ai/parity.md`
   se rellena auditando la app real en ese commit, no de memoria.
2. **Durante el desarrollo iOS**: la paridad se mide contra ese baseline. Una capacidad Android
   posterior al baseline entra como fila nueva con su sprint; no bloquea la primera entrega.
3. **Tras la primera entrega en TestFlight**: toda fila nueva nace con `ios: pendiente` y sprint
   asignado; `pnpm check:parity` impide que se quede sin dueño.
4. Si el baseline cambia de forma que invalida un escenario, el escenario se actualiza en el mismo
   PR que rompe el contrato. Nunca se "arregla" el test para que pase sin cambiar la spec.

## 13. Riesgos

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| El patrón visual no gusta y hay que rehacer pantallas | Media | G1 temprana con 2–3 pantallas; el resto hereda |
| Deriva de comportamiento entre apps | Media | Escenarios compartidos + `check:parity` en CI |
| Bug de seguridad en deep links / keychain | Media (ya ocurrió en Android) | Auditoría iOS con checklist propio, agente distinto |
| Revisión de Apple rechaza o retrasa | Media | TestFlight primero; ATS y privacidad documentados desde el inicio |
| Cuenta de organización retrasa el arranque (D-U-N-S) | Baja si es individual | Cuenta individual para uso familiar |
| Fatiga: dos UIs para siempre | Alta | Se asume; el coste recurrente es UI, no lógica (≈8–11 % duplicable) |
| Sensación "no nativa" | Baja con SwiftUI | Nada de wrappers; 5 días de freelance iOS en el repaso final (recomendado) |

## 14. Coste y fases

| Fase | Contenido | Esfuerzo equivalente | Calendario con multiagente | Puerta |
|---|---|---|---|---|
| 0 | Spec aprobada, cuenta Apple, baseline congelado | 2–3 d | 3–5 d (trámite en paralelo) | Aprobación |
| 1 | `spec/mobile/` + generadores + escenarios | 10–14 d | 6–8 d | G0 |
| 2 | Andamiaje Xcode + CI `ios` + AASA + ATS | 6 d | 5–6 d (paralelo) | G0 |
| 3 | Núcleo Swift: cliente, DTOs, sesión, formateadores, estado | 15–20 d | 8–10 d (serie) | G0 |
| 4 | 10 pantallas SwiftUI | 30–40 d | 10–14 d (fan-out) | **G1** |
| 5 | Integraciones nativas | 8–10 d | 6–8 d | **G2** |

Total ≈ **45–60 días de calendario**, con **4–6 días del propietario** (decisiones, G1, G3, trámite
y auditoría). Estimación de mercado si se externalizara: 56–82 jornadas, 19k–35k €.

## 16. Arranque (cuando el propietario termine lo actual)

1. Mergear a `staging` lo que esté en curso y etiquetar el baseline (§12.1).
2. Aprobar esta spec y cerrar D1–D5.
3. Crear `docs/tasks/sprint-NN-ios-app/` y su plan en `docs/superpowers/plans/`.
4. Abrir la cuenta Apple (individual) el primer día: es lo que no se puede acelerar después.
5. Fase 1 antes que cualquier pantalla: sin escenarios no hay garantía, y a 19k líneas el arnés
   cuesta la mitad que con dos apps vivas.
