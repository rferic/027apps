# Spec: backup y recuperación de la base de datos

- **Fecha:** 2026-10-26
- **Estado**: propuesta aprobada para implementación (sprint-infra, task-09)
- **Ámbito**: base de datos de producción (Postgres de Supabase) y su recuperación
- **Relacionado**: [`docs/infrastructure.md`](../../infrastructure.md), [`docs/flows/cicd.md`](../../flows/cicd.md#backups)

## 1. Problema

El plan free de Supabase **no incluye backups**: los backups diarios y el PITR son
funciones de los planes Pro/Team/Enterprise. La documentación oficial recomienda exportar
uno mismo y mantener copias off-site. Hoy 027Apps no tiene ninguna copia: perder el
proyecto (cierre de cuenta, pausa prolongada, borrado accidental, migración defectuosa)
significa perder todos los datos de la familia.

El esquema ya vive en git como migraciones, así que **la BD es reemplazable; el dato no**.
El objetivo del backup no es "tener un fichero", es poder **reconstruir la instancia en
otro proveedor** sin depender de Supabase.

## 2. Objetivo y no objetivos

**Objetivo**

1. Dump lógico diario de la BD, cifrado, en almacenamiento de **otro proveedor**.
2. Recuperación documentada y probada (runbook + simulacro) desde un portátil, sin
   depender de GitHub ni de Supabase.
3. Coste 0 (dentro de free tiers) y automatización sin intervención.

**No objetivos (v1)**

- Ficheros de Storage (bytes). Se documenta el método (S3 compatible) y queda como
  tarea aparte; el dump solo contiene metadatos de `storage`.
- PITR (restauración al segundo). La granularidad es diaria.
- Backups gestionados de Supabase (implican plan Pro desde 25 USD/mes).
- Copia secundaria en un segundo proveedor (3-2-1 completo). Se documenta como opción.

## 3. Modelo de amenaza

| Escenario | ¿Cubierto? | Cómo |
|---|---|---|
| Borrado accidental de datos | Sí | Restaurar el snapshot del día anterior (`--schema public`) |
| Migración destructiva | Sí | Backup previo manual (`workflow_dispatch`) + restore |
| Proyecto Supabase borrado o cuenta cerrada | Sí | Dump en R2/B2 + proyecto nuevo + runbook |
| Free tier pausado por inactividad | Sí (datos) | Keep-alive + backup; al reactivar, restore si hiciera falta |
| Pérdida de acceso a GitHub | Sí | Script ejecutable en local con secretos del gestor de contraseñas |
| Pérdida del bucket de backup | No | Mitigación opcional: `restic copy` a un segundo bucket |
| Pérdida de `RESTIC_PASSWORD` | No | Contraseña en gestor + copia impresa; sin ella el repo es ilegible |
| Ficheros de Storage | No (v1) | Pendiente: sync S3 (ver `docs/infrastructure.md`) |
| Corrupción silenciosa del backup | Mitigada | `pg_restore --list` + `restic check` diarios + simulacro trimestral |

## 4. Decisión

| Pieza | Decisión | Por qué |
|---|---|---|
| Formato | `pg_dump --format=custom --no-owner` (un `.dump`) | Restaurable con `pg_restore`, comprimido, portable entre proyectos; incluye `auth` y `storage` (esquemas) |
| Transporte/cifrado | [restic](https://restic.net) sobre endpoint S3 compatible | Cifrado autenticado, deduplicación, retención y `check` en una sola herramienta; binario único y versionado |
| Destino | Cloudflare R2 (o Backblaze B2), bucket privado | Otro proveedor distinto de Supabase y de GitHub; 10 GB gratis (la BD son MBs) |
| Cuándo | Cron diario 03:42 UTC + `workflow_dispatch` | Un día de pérdida máxima; ejecución manual antes de cambios destructivos |
| Retención | 7 diarios / 4 semanales / 12 mensuales | Cubre error humano reciente y recuperación a largo plazo |
| Ejecución | `scripts/backup/backup.sh` (CI y local) + `.github/workflows/backup.yml` | El mismo código corre sin GitHub: requisito del modelo de amenaza |
| Restauración | `scripts/backup/restore.sh` (`--schema public` por defecto, `all` para rescate) | Un comando para el runbook y el simulacro |
| Vigilancia | Fallo del workflow (email de GitHub) + ping opcional a healthchecks.io | Detecta también "el cron dejó de ejecutarse" |
| Documentación | `docs/infrastructure.md` (runbook) + `docs/flows/cicd.md` (CI) | La recuperación debe ser ejecutable por alguien sin contexto |

### Alternativas descartadas

| Alternativa | Motivo |
|---|---|
| Backups del plan Pro de Supabase | Coste mensual; y no protegen del cierre de cuenta (siguen dentro de Supabase) |
| Artifacts de GitHub Actions | Caducan a los 90 días y viven en la misma cuenta que puede perderse |
| `supabase db dump` (SQL plano) | Más pesado de restaurar y sin cifrado/retención; el CLI sigue usando `pg_dump` por debajo |
| Cron en un VPS propio | Un servidor más que mantener y otro punto único de fallo |
| `age`/GPG + `rclone` | Cifra y sube, pero sin retención ni verificación de integridad propias |
| `borg` | Excelente, pero restic es más simple de instalar desde un binario y soporta S3 nativo |

## 5. Formato y semántica del artefacto

- Un fichero `027apps.dump` por snapshot, formato custom de `pg_dump`, sin owners
  (`--no-owner`: el rol `postgres` del proyecto nuevo recrea la propiedad).
- Incluye los esquemas que ve el rol `postgres`: `public` (producto), `auth` (usuarios),
  `storage` (metadatos). **No** incluye los bytes de los buckets.
- Restauración normal (`--schema public`): limpia y recrea el esquema de producto en una
  BD existente. Es la ruta para un proyecto Supabase nuevo.
- Restauración de rescate (`--schema all`): vuelca el dump completo sin `--clean`, pensada
  para una BD vacía. Restaurar `auth` sobre un proyecto Supabase vivo choca con objetos
  gestionados por la plataforma; los usuarios se recuperan de forma *best-effort* (hashes
  incluidos) y, si GoTrue no arranca, se restablecen contraseñas.
- Los roles estándar (`anon`, `authenticated`, `service_role`, `postgres`) los crea el
  proyecto Supabase; por eso no se hace dump de roles de clúster.

## 6. Seguridad y secretos

- Los secretos solo viven en GitHub Secrets y en el gestor de contraseñas; nunca en git,
  logs ni argumentos impresos. `guard-secrets` sigue aplicando.
- Credenciales S3 **con alcance a un único bucket** (Object Read & Write), no a la cuenta.
- `RESTIC_PASSWORD` es la llave maestra del backup: gestor de contraseñas + copia impresa.
  Sin ella, el bucket es ruido cifrado.
- Los pasos de CI se omiten si faltan secretos (fork o repo recién clonado), sin fallar.

## 7. Criterios de aceptación

1. `scripts/backup/backup.sh` produce un dump válido y lo sube a un repo restic; verificado
   de extremo a extremo contra Postgres real (dump → restore → filas).
2. `scripts/backup/restore.sh` restaura el snapshot más reciente (`public` y `all`).
3. `.github/workflows/backup.yml` corre a diario, con permisos mínimos y `concurrency`.
4. Sin secretos, el workflow termina en verde omitiendo los pasos.
5. `docs/infrastructure.md` contiene inventario, retención, escenarios y runbook; `cicd.md`
   refleja el workflow y los secretos.
6. Simulacro de restauración definido (trimestral) y registrado en el runbook.
7. Auditoría de seguridad antes de `finalizada`.

## 8. Riesgos y decisiones abiertas

- **Drill no automatizado**: restaurar de verdad requiere un proyecto Supabase desechable
  (o Supabase self-hosted). Se hace a mano cada trimestre; automatizarlo es trabajo futuro.
- **Storage**: hasta que exista un bucket con datos reales, el backup no cubre ficheros.
- **Copia secundaria**: `restic copy` a un segundo bucket (otro proveedor) cierra el
  escenario "pierdo el bucket"; se documenta como opcional, no se implementa en v1.
- **Versión de `pg_dump`**: el CI instala el cliente 17; si el proyecto se queda en una
  major más nueva, hay que subir el cliente (el `pg_dump` viejo se niega a dumpear).
