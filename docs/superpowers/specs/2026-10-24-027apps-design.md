# Diseño de proyecto — 027Apps (plataforma familiar modular)

**Fecha:** 2026-10-24
**Estado:** Aprobado por el usuario (2026-10-24)
**Repositorio:** por crear en `~/Sites/rferic` → `github.com/rferic/027apps` (liberar el
nombre del repo antiguo, ver §14)

---

## 1. Intención y porqué

Plataforma de apps modular para **familia y amigos cercanos** que absorbe, módulo a módulo,
las apps de terceros que la familia usa hoy (Splitwise, apps de tareas, calendario…).
El objetivo es dejar de depender de terceros y tener los datos bajo control propio.

El proyecto es **sucesor espiritual de 027apps** (`~/Sites/027apps`), que se abandonó por
problemas de proceso, no de idea. Las lecciones de 027apps son requisitos de este diseño:

1. **Las convenciones deben ser ejecutables, no memorizadas.** En 027apps había que repetir
   constantemente instrucciones a la IA (generación de traducciones, estilos…) porque nada
   las forzaba por sistema. Aquí toda convención vive en ficheros, scripts o CI.
2. **Coherencia estética desde el día 1.** En 027apps cada módulo tenía su propio estilo.
   Aquí un design system con tokens es la única vía de escribir UI.
3. **Mobile-first real.** En 027apps se empezó por web y la app móvil fue "una tortura".
   Aquí el usuario final solo tiene app móvil nativa; la web es exclusivamente de administración.
4. **Seguridad de primera clase** (RLS, secrets, OWASP en revisión), no añadida a posteriori.
5. **MCP de primera clase**: la plataforma se expone a agentes IA desde el inicio.

## 2. Producto

- **App usuario final**: app móvil nativa **Kotlin + Jetpack Compose**, **100% móvil** y
  **solo Android por ahora** (APK instalable por enlace directo, sin tiendas ni cuentas de
  desarrollador). Los usuarios finales no tienen web. La app se conecta a la instancia
  propia configurando la URL del servidor en el login (o escaneando un QR). Las
  actualizaciones se distribuyen como nuevas APK por enlace; el flujo de actualización se
  definirá en las tareas de distribución.
- **Web de administración**: panel solo para administradores del grupo (gestión de usuarios,
  invitaciones, módulos instalados, importaciones, API keys/MCP).
- **Multi-instancia por despliegue propio**: el repo es **público** y cualquier persona puede
  montar su propia instancia creando **sus propias cuentas cloud gratuitas** (Supabase + Vercel
  y similares). No se exige Docker ni máquina propia (queda como opción futura, no como
  requisito de instalación).
- **Acceso privado**: cada instancia es privada; solo acceden usuarios invitados.
- **Infra gratuita**: la instancia del autor funciona íntegramente en free tiers.
- **Idiomas al lanzamiento**: español, catalán, inglés e italiano. La infraestructura i18n
  debe permitir añadir idiomas sin esfuerzo (pipeline automático).

## 4. Capacidades transversales (Core)

Tratadas como **capacidades de la plataforma**, no de cada módulo. Todo módulo nuevo las
hereda al nacer.

- **Realtime**: cambios visibles al instante entre miembros (Supabase Realtime, canales por
  grupo, eventos tipados).
- **Notificaciones**: push nativo Android + email. La integración concreta de push (p. ej.
  Firebase Cloud Messaging) se especificará al definir esa tarea, teniendo en cuenta que
  cada instalación auto-hospedada tendrá sus propias credenciales.
- **MCP**: endpoint MCP con SDK oficial, autenticación por API keys con scopes por módulo,
  tools por módulo + tools core. UI de gestión de keys en el admin.
- **Dark mode**: tokens semánticos con modo claro/oscuro desde el primer componente.
- **i18n**: claves en 4 locales; script de sincronización de claves + check de CI que **falla
  el build** si los locales no tienen exactamente las mismas claves; agente traductor para
  generar traducciones iniciales.
- **Auth y grupos**: Supabase Auth + tabla `profiles` propia (patrón ya validado en
  027apps), invitaciones por email, roles admin/member por grupo. El **método de login se
  decide al especificar el Core**; candidatas: magic link por email (sin contraseñas; SMTP
  propio obligatorio en el setup) y **QR + código de emparejamiento** (pair login ya
  existente en 027apps, útil para TV/dispositivos compartidos). Bootstrap decidido: el
  primer usuario registrado de una instancia nueva es `super_admin`.
- **Participantes ficticios**: cualquier módulo puede referenciar participantes que no están
  registrados (`kind: user | fictitious`), con **claiming**: si la persona ficticia se
  registra después, hereda su historial.
- **Sistema de módulos**: cada módulo es un paquete del monorepo con `manifest.json`
  (DDL con rollback, rutas, vistas, permisos, widgets, tools MCP, claves i18n). Patrón
  heredado de 027apps. Semántica decidida: **instalación global por instancia** (el DDL es
  global por naturaleza) + **activación por grupo** (qué grupos ven el módulo). Las
  tareas de fundaciones fijan el contrato: formato de manifest, script de registry y skill
  `new-module`; el instalador en runtime es una tarea del Core y lo estrena el primer módulo.
- **Seguridad**: RLS en todas las tablas (scoped por grupo), suite de tests que intenta
  accesos cruzados entre grupos, secrets cifrados, revisión OWASP en QA para cambios de
  auth/permisos.

## 5. Objetivos, no-objetivos y anti-objetivos

**Objetivos**
- Reemplazar Splitwise con datos reales importados (el importador es el puente de adopción).
- Consistencia total de estilo e i18n sin esfuerzo manual ni memoria.
- Cualquier persona técnica monta su instancia en ~15 minutos siguiendo la guía.
- El usuario humano no revisa código: aprueba specs, diseños y resultados.

**No-objetivos (esta fase o definitivamente)**
- Publicar en tiendas comerciales: la distribución es por enlace (APK en Android,
  TestFlight en iOS). Ver §6.
- Soporte iOS (por ahora): Android-only decidido; iOS se evaluará cuando haya necesidad
  real (ver §6).
- Monetización (por ahora).
- Alojamiento gestionado por nosotros ("multi-tenant SaaS"): cada instancia es de quien la monta.
- 6 idiomas al lanzamiento (4; ampliable).
- Migrar datos desde 027apps (no se importa nada de allí).
- Módulo de IA en el arranque.

**Anti-objetivos (sería un fracaso aunque funcionara)**
- Convenciones que dependan de la memoria de la IA o del humano.
- Módulos estéticamente dispares.
- Seguridad añadida a posteriori o RLS parcial.
- Que el usuario tenga que repetir instrucciones o tocar código.

## 6. Enfoques considerados (stack)

| Enfoque | Veredicto |
|---|---|
| **A. Next.js + Supabase + Vercel** | **Elegido.** Auth/Realtime/Storage/RLS gestionados (menos código de seguridad propio), instalación por terceros = crear cuentas gratis y desplegar, velocidad hacia producto |
| B. Next.js + Postgres propio + auth propia (better-auth) | Máximo control y auto-hospedaje Docker trivial, pero reconstruye auth/realtime/push y centraliza el riesgo de seguridad en código propio. Descartado al aclararse que "montársela" = cuentas cloud propias, no Docker local. Queda documentada como alternativa futura |
| C. PWA separada + backend API dedicado | Duplicación y piezas extra sin beneficio a esta escala. Descartado |

**Cliente de usuario (revisión del diseño, 2026-10-24):** app Android **nativa** con
Kotlin + Jetpack Compose — decisión del usuario. La lección de 027apps no era "no hagas
nativa", sino no hacer la app móvil un puerto tardío con estilos propios: aquí la app móvil
es el cliente principal, con tokens de diseño y contratos API definidos en común con la
plataforma desde el día 1.

**Mitigaciones de A (requisitos documentados, no notas al pie):**
- *Pausa del free tier de Supabase por inactividad (~1 semana)*: keep-alive automático
  (GitHub Action diario con ping a la API), documentado en la guía de instalación.
- *Límite de emails de auth del free tier*: configuración de SMTP propio (p. ej. cuenta
  Gmail con app password) como parte del setup, patrón ya validado en 027apps.
- *Migraciones para terceros*: documentadas vía Supabase CLI (`supabase db push`); la
  instancia del autor las aplica automáticamente en CI al hacer merge. El CI de forks sin
  secrets degrada con elegancia: los pasos de deploy/E2E/keep-alive se omiten cuando faltan
  las variables correspondientes. El setup inicial es **guía + variables de entorno**;
  un asistente in-app de primer arranque queda para después (no bloquea el objetivo de
  ~15 minutos).
- *Distribución sin tiendas*: **decidido: solo Android por ahora** — APK por enlace directo
  (gratis, sin cuenta de desarrollador). iOS queda aplazado; cuando toque, se evaluará
  construir un cliente iOS (p. ej. SwiftUI o Flutter) y el método de distribución, con el
  coste adicional que eso implique.

## 8. Modelo de datos Core (borrador para el builder)

```sql
profiles            (id = auth.users.id, display_name, locale, is_super_admin)
groups              (id, slug, name, created_by)
group_members       (group_id, user_id, role: admin|member)
invitations         (group_id, email, token, expires_at, invited_by)
participants        (id, group_id, kind: user|fictitious, user_id nullable,
                     display_name, claim_token nullable)  -- claiming de ficticios
api_keys            (id, group_id, key_hash, type: api|mcp, scopes text[], last_used_at)
device_tokens      (id, user_id, platform (android ahora; ios si algún día),
                    expo_push_token, last_seen_at)
instance_settings   (key, value_encrypted)  -- secrets por instancia cifrados con
                                            -- clave maestra en env: SMTP, futuras
                                            -- LLM keys BYOK, secrets de clientes MCP
```

Decisión de secrets: lo **por-instancia en runtime** vive cifrado en
`instance_settings`; lo **de plataforma** (claves Supabase, clave maestra) en variables de
entorno. Tablas de módulo con dinero (Split Expenses) guardan `currency` y `exchange_rate`
en cada transacción (ver límites v1 en §3).

- Todas las tablas de módulo llevan `group_id` y RLS scoped al grupo.
- Los módulos referencian `participants`, nunca `profiles` directamente: así los ficticios
  y el claiming son transversales.

## 9. Forma de trabajo y metodología

**Spec-Driven Development con superpowers**: cada cambio sigue
brainstorming → spec en `docs/superpowers/specs/` → plan en `docs/superpowers/plans/` →
implementación con TDD (test primero) → revisión. Nada se implementa sin spec aprobada.

**Orquestación de agentes (modelo aprobado):**
- Plano: orquestador (sesión principal) + subagentes especializados. Sin jerarquías profundas.
- **Contexto inyectado, nunca recordado**: cada subagente recibe un pack armado desde
  ficheros (sección de spec + convenciones + criterios de aceptación).
- El bucle TDD lo ejecuta un solo agente (partirlo pierde intención).
- Revisión con ojos nuevos: QA (bugs, edge cases, OWASP), revisión de estilo, cada uno como
  agente aparte que no escribió el código. **Y auditoría de seguridad obligatoria antes de
  marcar cualquier tarea como `finalizada`** — requisito explícito del usuario (2026-10-24).
- Paralelización solo de trabajo realmente independiente (p. ej. traducciones de 4 locales).
- **Determinismo antes que agentes**: typecheck, lint, tests, sync de claves i18n y CI
  rechazan lo mecánico; los agentes solo deciden lo semántico.

**Convenciones ejecutables (la cura del dolor de 027apps):**
- `AGENTS.md` en raíz: obligaciones por tipo de tarea, checklist obligatoria.
- Skills del proyecto (`.opencode/skills/`): `i18n-sync`, `new-module`, `review`, etc.
- Scripts: sincronización de claves i18n, generación de tipos, generación de registry.
- CI como juez final: si algo se salta las convenciones, el build falla.

**Git y releases (gestionados íntegramente por agentes):**
- Ramas `feature/*` / `fix/*`, conventional commits, PR por change, squash merge a `main`.
- `main` siempre desplegable; preview deploy por PR (el usuario acepta resultados ahí).
- Changelog y versionado automáticos.

**Rol del usuario humano:** aprueba specs y diseños, acepta demos/previews, responde
preguntas de producto. **No revisa código ni PRs.**

## 10. Diseño y estilo

- Design system propio: tokens semánticos (color, tipografía, espaciado, radios, sombras)
  en claro/oscuro como única fuente de verdad. Prohibido hardcodear colores — CI + revisión
  de estilo lo vigilan (en 027apps se acumularon 220+ colores hardcodeados).
- Los módulos **solo** consumen componentes del DS; nada de estilos ad-hoc por módulo.
- Storybook obligatorio para componentes del DS.
- Primer sprint: definición de identidad visual (se propondrán 2–3 direcciones al usuario) y
  mockups de las pantallas clave de Split Expenses antes de implementar su UI.

## 11. Planificación: backlog de tareas y sprints

No hay fases predefinidas: el trabajo se organiza como **backlog de tareas** y **sprints**.

**Sprint** = unidad de trabajo. Al arrancar cada sprint, el orquestador propone tareas
candidatas (con dependencias y prioridad) y el usuario escoge qué se implementa. Al cerrar,
toda tarea queda `finalizada` o vuelve al backlog con lo aprendido.

**Tarea** = unidad mínima planificable. Un fichero por tarea en `docs/tasks/` con
metadatos legibles por máquina (id, título, área, estado, sprint, spec/plan enlazado).
Estados, en este orden:

| Estado | Significado |
|---|---|
| `pendiente` | En el backlog, sin empezar |
| `en curso` | En implementación (con su spec/plan si lo requiere) |
| `test` | Implementada y en verificación: QA con ojos nuevos + **auditoría de seguridad**, CI verde, aceptación del usuario cuando aplica |
| `finalizada` | Verificada, merge a `main` y desplegada |

Los estados viven en los ficheros — nunca en la cabeza de nadie.

**Backlog inicial por áreas** — cada tarea de definición produce un artefacto concreto
(documento, pipeline, skill o código andamiado); nada queda "definido a medias". Al
planificar el primer sprint se redactan como ficheros en `docs/tasks/`.

*Definiciones — infra técnica:*
- Repo y scaffold: repo GitHub público, monorepo con app Android Kotlin/Gradle + admin
  Next.js en Vercel, Supabase conectado y tooling completo para ambas apps (lint, format,
  typecheck, tests)
- Pipeline CI/CD completo: gates (typecheck, lint, unit, build, check de claves i18n, E2E),
  preview deploy del admin por PR, producción en merge, build y publicación del APK Android
  como artefacto descargable, keep-alive de Supabase, migraciones automáticas, degradación
  elegante en forks sin secrets
- Releases y versionado: conventional commits, tags, changelog automático
- Observabilidad: Sentry, logs, guía de depuración

*Definiciones — reglas de código:*
- `AGENTS.md` completo: obligaciones por tipo de tarea
- Reglas de clean code: naming, estructura de carpetas, patrones permitidos/prohibidos,
  límites de complejidad, reglas ESLint/Prettier propias
- Patrones arquitectónicos por ADR: server actions vs API routes, validación (zod),
  manejo de errores, estado y fetching, fechas y moneda
- Definition of Done por tipo de tarea (código, doc, diseño)

*Definiciones — proceso y responsabilidades:*
- Flujos documentados paso a paso: feature, bugfix, hotfix, release, nuevo módulo,
  traducción
- Responsabilidades de agentes: quién implementa, quién revisa (QA/estilo/seguridad),
  quién decide, qué le llega al usuario en cada paso
- Estrategia de testing: unit/integración/E2E/RLS/visual, coverage mínimo, fixtures
- Flujo i18n completo: generación de claves, sync entre locales, traducción con agente,
  check de CI

*Definiciones — estilo, diseño y branding:*
- Branding: logo/wordmark "027Apps", icono de app (iOS/Android) + favicons del admin web,
  splash, paleta
  de marca, voz y tono de los textos (microcopy), imagen de preview social (OG)
- Identidad visual: 2–3 direcciones → elección
- Design tokens completos: claro/oscuro, tipografía, espaciado, radios, sombras, iconos
- Componentes base del design system (10–15) + Storybook
- Patrones UX: navegación móvil, estados de carga/vacío/error, accesibilidad, feedback
- Mockups de las pantallas clave del primer módulo

*Definiciones — seguridad:*
- Checklist OWASP del proyecto + modelo de amenazas simple
- Política de secrets, patrón RLS estándar, auditoría de dependencias (dependabot)

*Definiciones — para la IA:*
- Skills del proyecto: i18n-sync, new-module, revisiones, generación de tipos
- Onboarding de sesión: qué carga una sesión nueva y en qué orden
- Docs fundacionales: guía de instancia propia (fork → Supabase → Vercel, ~15 min),
  arquitectura, ADRs, CONTRIBUTING

*Core* — **bloqueado por las definiciones anteriores**: login (aquí se decide entre magic
link y QR + código), perfiles, grupos/roles/invitaciones, participants (ficticios +
claiming), instalador de módulos en runtime (DDL y rollback), pipeline i18n operativa,
infra de realtime, infra de notificaciones (push nativo + email), shell del admin, esquema de
BD (profiles, groups, members, invitations, participants, api_keys, device_tokens,
instance_settings) con RLS y tests de aislamiento.

*Módulos* — se detallan al especificar cada módulo. Split Expenses encabeza la cola; el
orden del resto se decide al planificar cada sprint.

**Reglas**: las tareas de Core **no empiezan** hasta que las definiciones que les afectan
están `finalizada`; las tareas de módulos dependen de las de Core (el backlog registra
dependencias para que la elección de sprint sea informada); las tareas grandes llevan spec
propia antes de pasar a `en curso`; los lotes de tareas pequeñas pueden compartir el plan
del sprint.

## 12. Lecciones de 027apps (guía explícita para el builder)

**Repetir**: contratos API tipados, manifests de módulos, sistema de secrets cifrados,
modelo contable puro en gastos (gastos inmutables + transfers como único mecanismo de
saldo; sin conceptos tipo `settled`), Storybook, preview-first.

**No repetir**: web-first con móvil como puerto tardío, colores hardcodeados, strings sin
i18n, módulos con estilo propio, convenciones en la cabeza del usuario, jerarquías de
agentes con contexto mal inyectado.

**Sobre reutilización de código**: el proyecto es **greenfield** — no se copia código de
027apps wholesale (otra arquitectura, otro enfoque mobile-first, repo público con estándares
altos). Los algoritmos con valor probado (p. ej. liquidación óptima de mínimos movimientos)
se portan revisados y con tests propios; el resto se re-deriva de las lecciones documentadas.

## 13. Qué queda al builder

Detalles de UX de cada pantalla (con los mockups como guía), definición exacta de tablas de
módulo, elección de librerías concretas dentro del stack (p. ej. qué librería de gráficos),
umbrales de coverage, estructura fina de carpetas, naming exacto de eventos realtime.
