# Spec — Core: MCP del Core (sprint 04, task 05)

**Fecha:** 2026-10-26
**Estado:** Borrador para aprobación del usuario
**Base:** [spec de API v1 §3.8](2026-10-25-api-v1.md) (MCP sobre el mismo backbone, clave de instancia `027_svc_`, alcance v1) · [ADR 0004](../../adr/0004-bordes-y-capa-de-aplicacion.md) (puertas delgadas, mismos casos de uso, representación compartida) · [spec de tokens §3/§5](2026-10-25-token-model.md) (taxonomía de claves, scopes por acción) · [ADR 0007](../../adr/0007-manejo-de-errores.md) (códigos de error estables) · [spec de datos](2026-10-26-core-data-model.md) (task-01) · [spec de API del Core](2026-10-26-core-api.md) (task-02) · [spec de módulos](2026-10-26-modulo-system.md) (task-03: `mcp_tools` del manifest)
**Decide el usuario:** dos rutas (pública/admin), API keys en v1 con OAuth diferido, catálogo Core, `mcp_exposed` por módulo (2026-10-26)

## 1. Objetivo

Exponer la instancia a **agentes de IA** por el **Model Context Protocol (MCP)**, con el **mismo backbone** que la API REST: las tools llaman a los **mismos casos de uso** y devuelven **la misma representación compartida** (ADR 0004 §7). Nada de lógica duplicada ni de contrato paralelo.

**Límite de alcance:** esta spec fija el transporte, la autenticación, el catálogo de tools del Core, el contrato de tools de módulo, los errores y el rate limiting. **Las tools concretas de cada módulo** (su nombre, sus argumentos, su lógica) son de la spec de cada módulo; aquí se define **cómo se declaran y exponen**.

## 2. Transporte

- **Streamable HTTP** (el transporte `HTTP+SSE` está deprecado en la spec MCP vigente — `2026-07-28`).
- **Modo stateless**: una instancia de servidor + transporte **por request** (`sessionIdGenerator: undefined`), sin sesiones de servidor. Cada petición se autentica por sí misma, lo que encaja con un route handler de Next y no requiere afinidad de instancia.
- **SDK oficial** (`@modelcontextprotocol/sdk`, API v2: `McpServer` + `registerTool`). La versión exacta se fija en el plan de implementación; el contrato no depende de ella.
- **Protocolo**: se declara la versión soportada en el handshake y se rechaza una versión incompatible con el error estándar del protocolo.

### 2.1 Endpoints (decisión del usuario)

| Endpoint | Clave aceptada | Para quién |
|---|---|---|
| **`/mcp`** | **delegada** `027_usr_…` (actúa como su usuario) | agentes personales del usuario |
| **`/mcp/admin`** | **instancia** `027_svc_…` (sin identidad de usuario) | agentes de administración de la instancia |

- **Misma implementación**, montada dos veces. Cada ruta **rechaza la clave del otro tipo** (`401`), de modo que una clave de instancia no puede usar el servidor personal ni al revés.
- **Fuera de `/api/v1`** a propósito: MCP es un protocolo distinto (JSON-RPC sobre HTTP), no un recurso REST. Se documenta como decisión consciente frente al API-first de `/api/v1`.
- `GET`/`DELETE` no se usan (stateless); solo `POST`.

## 3. Autenticación

- `Authorization: Bearer <clave>` — las claves del modelo de tokens ya aprobado (opacas, hasheadas en BD, revocación instantánea, expiración opcional).
- **`/mcp`** exige `kind = delegated`; **`/mcp/admin`** exige `kind = service`.
- Fallos: **401** (clave ausente/inválida/revocada/caducada), **403** (`insufficient_scope` cuando la clave no tiene el scope de la tool concreta). Sin enumeración: el mensaje no distingue "no existe" de "sin permiso" (ADR 0007 §3).
- **Scopes por tool**: cada tool declara el/los scopes que exige; el guard compartido los comprueba (ADR 0004 §2). En `/mcp` el acceso efectivo es `min(scopes de la clave, permisos del usuario)` + `has_module_access` (task-01). En `/mcp/admin`, los scopes de la clave.
- **Desviación documentada de la spec MCP (OAuth 2.1)**: la spec MCP exige OAuth 2.1 + validación de audience (RFC 8707) + registro dinámico de clientes para servidores remotos. En v1 usamos **API keys estáticas** porque:
  1. la instancia es **autoalojada y privada**, y las claves las emite su propio administrador (no hay servidor de autorización de terceros);
  2. la **intención de "audience"** se cumple igual: una clave es de **esta instancia** y de ninguna otra;
  3. ya existe un **modelo de tokens aprobado** (revocación instantánea, scopes finos, expiración) que cubre el caso de uso.
  **OAuth 2.1 queda registrado como backlog** (`docs/tasks/sprint-mcp-oauth/task-01.md`): autorización, DCR, `/.well-known/oauth-protected-resource`, audience y consentimiento.
- **Sin secrets en logs ni en respuestas**: la clave nunca se refleja; el `audit` guarda la fila de la clave, no el secreto (spec de tokens §6).

## 4. Catálogo de tools del Core (v1)

Solo **lectura**, mínimas (decisión del usuario):

| Tool | Scopes | Devuelve (`structuredContent`) | Disponible en |
|---|---|---|---|
| `instance_get` | `instance:read` | metadatos no sensibles (versión, locales activos, moneda por defecto, estado) — **nunca** `settings_public` con secretos ni settings privados | `/mcp` y `/mcp/admin` |
| `modules_list` | `modules:read` | catálogo: `key`, `name`, `version`, `state`, `is_public`, `mcp_exposed` | `/mcp` y `/mcp/admin` (en `/mcp`: solo los módulos a los que el usuario tiene acceso) |
| `categories_list` | `user_categories:read` | categorías de usuarios (+ `member_count`) | solo `/mcp/admin` |
| `users_list` | `users:read` | usuarios: `id`, `display_name`, `role` (**sin email** ni datos sensibles) | solo `/mcp/admin` |

> El email **no** se expone por MCP: no es necesario para operar y reduce el dato personal que un agente puede leer.

## 5. Tools de módulo (contrato)

- **Declaración** en el manifest (task-03): `mcp_tools: [{ name, description, scopes }]`. El nombre es **namespaced por módulo** (`<module_key>.<tool>`, p. ej. `split-expenses.expenses_list`) para evitar colisiones.
- **Implementación** en el código del módulo; el handler llama a su **caso de uso** (nunca reimplementa reglas).
- **Exposición** (decisión del usuario): **automática** al estar el módulo `active`, **salvo** que el admin lo apague por módulo con **`module_registry.mcp_exposed = false`** (delta a task-01; editable en el panel, sin desinstalar).
- **Permiso del usuario** (en `/mcp`): tool disponible solo si se cumplen **las tres**:
  1. el módulo está `active` **y** `mcp_exposed`;
  2. el usuario tiene acceso al módulo (`has_module_access`: público o `user_modules`);
  3. la clave delegada tiene el scope de la tool (`min(scopes de la clave, permisos del usuario)`).
- **`tools/list` filtrado**: devuelve solo las tools que el llamador puede ejecutar. Un agente no ve herramientas que no puede usar (menos ruido y menos superficie).
- **Escrituras permitidas** si la spec del módulo las declara (p. ej. crear un gasto): pasan por el mismo caso de uso, la misma validación zod y la misma transacción que el REST. **v1 del Core es solo lectura**; las escrituras llegan con las tools de cada módulo.

## 6. Contrato de entrada/salida

- **`inputSchema`**: **el mismo schema zod** de entrada del caso de uso/endpoint (fuente única del contrato, api-v1 §5).
- **`outputSchema`**: **el mismo schema zod del recurso** compartido. El SDK **valida** la salida contra él antes de responder, así que "MCP devuelve la misma representación que REST" pasa a estar **verificado por el SDK**, no por disciplina.
- **`structuredContent`**: la representación compartida (ADR 0004 §7), idéntica al REST y al `resource` de los eventos (task-04).
- **`content`**: texto legible para el modelo, **en inglés** (lingua franca técnica; el servidor no localiza — ADR 0007 §1).
- **Paginación**: los parámetros `offset`/`limit`/`cursor` del contrato v1 se exponen en las tools de listado; `meta` va en `structuredContent`.

## 7. Errores

- **HTTP**: `401` (autenticación), `403` (scope), `429` (rate limit), `500` (inesperado). Un error **de aplicación** en una llamada válida se devuelve como **error JSON-RPC** con HTTP 200 (comportamiento del protocolo).
- **Error JSON-RPC**:

  ```json
  { "jsonrpc": "2.0", "id": 7,
    "error": { "code": -32000, "message": "<default message en inglés>",
               "data": { "code": "<domain_code>", "details": [ … ] } } }
  ```

  - `data.code` = **el código estable del ADR 0007** (`validation_failed`, `not_found`, `insufficient_scope`, `conflict`, …). El cliente decide por el código, no por el texto.
  - `data.details` = solo para `validation_failed` (campos y reglas).
  - `message` = texto por defecto en inglés (no localizado).
  - **Nunca** stack, SQL, rutas internas ni secretos — ni en dev (ADR 0007 §5).

## 8. Rate limiting y auditoría

- **Rate limiting**: por **clave**, **30 req/min** (el umbral de terceros de task-02 §4); `/mcp` y `/mcp/admin` comparten bucket por clave. Exceso → **429** con `Retry-After`. Configurable por `settings` (`security.rate_limit.*`).
- **Auditoría**: cada llamada incrementa `audit` (`api_key_id` × tool, ventana agregada — spec de tokens §6). El "endpoint" registrado es **el nombre de la tool** (`split-expenses.expenses_list`), nunca el token.
- **`admin_actions`**: solo si una tool de módulo hace una mutación sensible (p. ej. invitar) — lo decide el caso de uso, no el transporte.

## 9. Decisiones tomadas (conversación de diseño, 2026-10-26)

| # | Decisión |
|---|---|
| A | **Streamable HTTP stateless** (HTTP+SSE deprecado), SDK oficial, versiones de protocolo declaradas |
| B | **Dos rutas, una implementación**: `/mcp` (clave delegada `027_usr_`) y `/mcp/admin` (clave de instancia `027_svc_`); cada una rechaza la clave del otro tipo |
| C | **API keys en v1**; **OAuth 2.1 diferido** al backlog con la desviación documentada (self-hosted, audience = instancia) |
| D | **Catálogo Core v1** (solo lectura): `instance_get`, `modules_list`, `categories_list` (admin), `users_list` (admin); sin email |
| E | **Tools de módulo** namespaced, expuestas **automáticamente** si el módulo está `active`, con interruptor **`mcp_exposed`** por módulo (delta a task-01) |
| F | **Permiso de usuario en `/mcp`** = módulo `active` + `mcp_exposed` + `has_module_access` + `min(scopes clave, permisos usuario)`; `tools/list` filtrado |
| G | **Contrato verificado**: `inputSchema`/`outputSchema` = schemas zod compartidos; `structuredContent` = representación compartida (el SDK valida) |
| H | **Errores**: JSON-RPC con `data.code` = código ADR 0007; HTTP 401/403/429/500; JSON-RPC error con HTTP 200 |
| I | **Rate limiting** 30 req/min por clave (bucket compartido) y **auditoría** por tool |

- **UI de gestión de claves MCP** en el panel → sprint-web (task-02 `/api-keys` + task-12 shell).

## 11. Criterios de aceptación

- `/mcp` y `/mcp/admin` responden por Streamable HTTP stateless con el SDK oficial; cada ruta rechaza la clave del otro tipo.
- El catálogo Core (§4) está implementado como tools de solo lectura con sus scopes; `tools/list` se **filtra** por lo que el llamador puede ejecutar.
- Las tools de módulo se declaran en el manifest con nombre namespaced y quedan expuestas solo si el módulo está `active`, `mcp_exposed` y (en `/mcp`) el usuario tiene acceso.
- `outputSchema`/`structuredContent` son los schemas y la representación compartidos; el SDK valida la salida.
- Los errores devuelven `data.code` del ADR 0007 y nunca filtran internos; 401/403/429 correctos.
- Cada llamada suma a `audit` por tool y respeta 30 req/min por clave.
- Coherente con api-v1 §3.8, spec de tokens §3/§5, ADR 0004/0007, task-01/02/03.
- Aprobada por el usuario y revisada por segundo agente (DoD de Docs).
