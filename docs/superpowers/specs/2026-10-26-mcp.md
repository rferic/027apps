# Spec — Core: MCP del Core y por módulo (sprint 04, task 05)

**Fecha:** 2026-10-26
**Estado:** Borrador para aprobación del usuario
**Base:** [spec de API v1 §3.8](2026-10-25-api-v1.md) (MCP sobre el mismo backbone, claves de instancia y delegadas, alcance v1 — **delta 2026-10-26**) · [ADR 0004](../../adr/0004-bordes-y-capa-de-aplicacion.md) (mismos casos de uso, representación compartida) · [spec de tokens §3/§5](2026-10-25-token-model.md) (taxonomía, scopes por acción) · [ADR 0007](../../adr/0007-manejo-de-errores.md) (códigos de error) · [spec de datos](2026-10-26-core-data-model.md) (task-01) · [spec de API del Core](2026-10-26-core-api.md) (task-02) · [spec de módulos](2026-10-26-modulo-system.md) (task-03: `mcp_tools`)
**Decide el usuario:** MCP **por módulo** + un general; catálogo con **acciones** (no solo consultas); idempotencia por id de cliente; `users_update` con `roles:assign` (2026-10-26)

## 1. Objetivo

Exponer la instancia a **agentes de IA** por **MCP**, con el **mismo backbone** que la API REST: las tools llaman a los **mismos casos de uso** y devuelven **la misma representación compartida** (ADR 0004 §7). Y con **capacidad de actuar**, no solo de consultar: invitar, gestionar usuarios y categorías, conceder acceso a módulos, y crear/editar datos de los módulos (p. ej. un gasto).

**Límite de alcance:** aquí se fija el transporte, la topología de endpoints, la autenticación, el catálogo **del Core**, el contrato de tools **de módulo**, los errores, la idempotencia y el rate limiting. Las **tools concretas de cada módulo** (argumentos y lógica) son de la spec del módulo.

## 2. Topología: un MCP por módulo + un general (decisión del usuario)

| Endpoint | Clave | Tools | Notas |
|---|---|---|---|
| **`/mcp`** | delegada `027_usr_…` | **Core de usuario**: `profile_get`, `profile_update`, `instance_get`, `modules_list` | el "general" del usuario; `modules_list` es el **descubrimiento** de a qué módulos puede conectar |
| **`/mcp/admin`** | instancia `027_svc_…` | **Core de administración** (§4): invitaciones, usuarios, categorías, acceso a módulos, settings no secretos, lecturas | el "general" del admin |
| **`/mcp/<module_key>`** | delegada `027_usr_…` | **solo las tools de ese módulo** | requiere módulo `active` + `mcp_exposed` + `has_module_access` |

**Regla de no duplicación:** cada tool vive en **un único endpoint**. Las tools de un módulo **no** aparecen en `/mcp`; el agente descubre sus módulos con `modules_list` y se conecta a los que le interesan.

**Ventajas de la topología por módulo**: `tools/list` corto (mejor selección del LLM), el permiso va en la URL, configuración independiente por agente en el cliente MCP, ciclo de vida limpio (módulo desactivado → su endpoint devuelve `404`), rate limiting y auditoría por módulo.

- **Palabras reservadas**: un módulo **no puede** llamarse `admin`, `mcp`, `api` ni `core` (invariante del manifest, task-03 §3) — así `/mcp/admin` nunca colisiona con un módulo.
- Cada ruta **rechaza la clave del otro tipo**: `/mcp` y `/mcp/<module>`, 401 con clave `service`; `/mcp/admin`, 401 con clave delegada.

## 3. Transporte

- **Streamable HTTP** (el transporte `HTTP+SSE` está deprecado en la spec MCP vigente, `2026-07-28`).
- **Stateless**: servidor + transporte **por request** (`sessionIdGenerator: undefined`), sin sesiones de servidor. Cada petición se autentica por sí misma (encaja con route handlers de Next y con varias instancias).
- **SDK oficial** (`@modelcontextprotocol/sdk`, API v2: `McpServer` + `registerTool`); versión exacta en el plan de implementación.
- **Versión de protocolo** declarada en el handshake; versión incompatible → error estándar del protocolo.
- Solo `POST` (`GET`/`DELETE` no aplican en stateless).
- **Fuera de `/api/v1`** a propósito: MCP es JSON-RPC sobre HTTP, no un recurso REST (decisión consciente frente al API-first de `/api/v1`).

## 4. Catálogo de tools del Core

### 4.1 `/mcp/admin` — acciones (decisión del usuario: MCP actúa, no solo consulta)

| Tool | Acción | Scopes |
|---|---|---|
| `invitations_create` | crear invitación (email, nombre, `user_category_id`, módulos) | `invitations:write` |
| `invitations_list` | listar invitaciones (estado) | `invitations:read` |
| `invitations_revoke` | revocar invitación | `invitations:write` |
| `users_list` | listar usuarios (filtros `q`, `module`, `category`) — **sin email** | `users:read` |
| `users_get` | detalle de usuario (sin email) | `users:read` |
| `users_update` | editar `display_name` y **`role`** | `users:write` + **`roles:assign`** |
| `users_deactivate` | desactivar usuario (soft; emite `user.deactivated` → hooks) | `users:write` |
| `categories_list` | listar categorías (+ `member_count`) | `user_categories:read` |
| `categories_create` | crear categoría | `user_categories:write` |
| `categories_update` | renombrar categoría | `user_categories:write` |
| `categories_delete` | borrar categoría (no revoca concesiones materializadas) | `user_categories:write` |
| `categories_add_member` | añadir usuario a categoría | `user_categories:write` |
| `categories_remove_member` | quitar usuario de categoría | `user_categories:write` |
| `categories_assign_module` | **dar un módulo a una categoría** (materializa `user_modules`) | `user_categories:write` + `modules:grant` |
| `categories_unassign_module` | quitar módulo de una categoría | `user_categories:write` + `modules:grant` |
| `modules_list` | catálogo (estado, `is_public`, `mcp_exposed`) | `modules:read` |
| `modules_grant` | conceder acceso a un módulo a **un usuario** | `modules:grant` |
| `modules_revoke` | revocar acceso (soft; re-grant lo restablece) | `modules:grant` |
| `settings_get` | leer settings **no secretos** | `settings:read` |
| `settings_update` | escribir settings **no secretos** | `settings:write` |
| `instance_get` | metadatos de la instancia | `instance:read` |

> `users_update` con `role` **incluido** (decisión del usuario): el scope `roles:assign` es el control — el usuario decide si se lo concede a la clave al crearla. Solo `super_admin` puede promocionar a `super_admin` (task-01 L).

### 4.2 `/mcp` — Core de usuario

| Tool | Acción | Scopes |
|---|---|---|
| `profile_get` | mi perfil | `profile:read` |
| `profile_update` | editar `display_name`, `locale`, `timezone` (**no** `role`) | `profile:write` |
| `instance_get` | metadatos no sensibles | `instance:read` |
| `modules_list` | **mis** módulos (públicos + concesiones; admins → todos) con `mcp_exposed` | `modules:read` |

### 4.3 `/mcp/<module_key>` — tools del módulo

- Solo las tools declaradas por ese módulo en su manifest (`mcp_tools`), **incluidas escrituras** (p. ej. `expenses_create`, `settle_up`).
- Disponibles solo si: módulo `active` **y** `mcp_exposed` **y** `has_module_access` **y** la clave tiene el scope de la tool (`min(scopes de la clave, permisos del usuario)`).
- `tools/list` **filtrado** por esos cuatro gates.
- **Escrituras** pasan por el mismo caso de uso, la misma validación zod y la misma transacción que el REST; los cambios sensibles se registran en `admin_actions`.

### 4.4 Fuera de MCP a propósito

| Excluido | Motivo |
|---|---|
| **Instalar / desinstalar / activar módulos** | ejecuta DDL y exige revisión humana del diff (task-03 decisión D) |
| **Crear / revocar API keys** | el secreto se muestra **una sola vez** (spec de tokens §6); se gestiona en el panel |
| **Settings `is_secret`** (SMTP, service account, BYOK) | un agente no lee ni escribe secretos |
| **Borrado destructivo de datos de dinero** | lo decide el módulo; el dinero no se borra (spec §12) |

## 5. Idempotencia de las escrituras (decisión del usuario)

Un agente puede **reintentar** una llamada; un reintento no puede duplicar una acción.

- **`create` con id natural**: el cliente **genera el `id` (UUID)** y lo envía; mismo `id` → **mismo recurso** (insert idempotente; si ya existe con el mismo contenido, se devuelve; con contenido distinto → `conflict`). Aplica a recursos con id: gastos, categorías, invitaciones.
- **Recursos sin id natural o acciones repetibles** (p. ej. una liquidación, un envío): campo opcional **`idempotency_key`** en la entrada; el caso de uso deduplica por `(clave de API, tool, idempotency_key)` y devuelve el resultado previo.
- El patrón es el **mismo en REST** (no solo MCP): el contrato de idempotencia no depende del transporte.
- **Nunca** idempotencia por "parecido" de contenido: solo `id` o `idempotency_key` explícitos.

## 6. Contrato de entrada/salida

- **`inputSchema`**: **el mismo schema zod** de entrada del caso de uso/endpoint (fuente única del contrato, api-v1 §5).
- **`outputSchema`**: **el mismo schema zod del recurso** compartido. El SDK **valida** la salida antes de responder → "MCP devuelve lo mismo que REST" queda **verificado por el SDK**.
- **`structuredContent`**: la representación compartida (ADR 0004 §7), idéntica al REST y al `resource` de los eventos (task-04).
- **`content`**: texto legible para el modelo, **en inglés** (el servidor no localiza — ADR 0007 §1).
- **Paginación**: `offset`/`limit`/`cursor` del contrato v1; `meta` en `structuredContent`.
- **Errores de validación** de `inputSchema` → `validation_failed` con `details` (no un error genérico del SDK).

## 7. Errores

- **HTTP**: `401` (autenticación), `403` (`insufficient_scope`), `404` (módulo no disponible en su endpoint), `429` (rate limit), `500` (inesperado). Error **de aplicación** en llamada válida → **error JSON-RPC con HTTP 200** (protocolo).
- **Error JSON-RPC**:

  ```json
  { "jsonrpc": "2.0", "id": 7,
    "error": { "code": -32000, "message": "<default message en inglés>",
               "data": { "code": "<domain_code>", "details": [ … ] } } }
  ```

  - `data.code` = código estable del ADR 0007 (`validation_failed`, `not_found`, `insufficient_scope`, `conflict`, `rate_limited`, `internal`…).
  - `data.details` solo en `validation_failed`.
  - **Nunca** stack, SQL, rutas internas ni secretos (ADR 0007 §5), ni en dev.

## 8. Rate limiting y auditoría

- **Rate limiting por clave**: 30 req/min (umbral de terceros, task-02 §4). El bucket es **por clave y por endpoint MCP** (permite dar más margen a un módulo de lectura); exceso → `429` + `Retry-After`. Configurable en `settings` (`security.rate_limit.*`).
- **Auditoría**: cada llamada incrementa `audit` (`api_key_id` × `"<module_key>.<tool>"` o `core.<tool>`, ventana agregada — spec de tokens §6). Nunca el token.
- **`admin_actions`**: las tools que mutan algo sensible (invitar, cambiar rol, conceder acceso, cambiar settings) lo registran **dentro de la transacción** del caso de uso.

## 8bis. Autenticación y desviación de la spec MCP

- `Authorization: Bearer <clave>` — claves del modelo de tokens aprobado (opacas, hasheadas, revocación instantánea, expiración opcional).
- **Desviación documentada (OAuth 2.1)**: la spec MCP exige OAuth 2.1 + audience (RFC 8707) + registro dinámico de clientes para servidores remotos. En v1 usamos **API keys** porque: (1) la instancia es **autoalojada y privada** y las claves las emite su propio administrador; (2) la intención de *audience* se cumple — la clave es de **esta instancia** y de ninguna otra; (3) el modelo de tokens aprobado ya cubre revocación y scopes finos. **OAuth queda en backlog**: `docs/tasks/sprint-mcp-oauth/task-01.md` (PKCE, DCR, `/.well-known/oauth-protected-resource`, audience, consentimiento).
- Sin secretos en logs ni respuestas; el `audit` guarda la fila de la clave, nunca el secreto.

## 9. Decisiones tomadas (conversación de diseño, 2026-10-26)

| # | Decisión |
|---|---|
| A | **Un MCP por módulo + uno general**: `/mcp` (Core usuario), `/mcp/admin` (Core admin), `/mcp/<module_key>` (módulo). Sin duplicar tools; `modules_list` como descubrimiento |
| B | **MCP actúa**, no solo consulta: catálogo Core con invitaciones, usuarios, categorías, acceso a módulos y settings no secretos; tools de módulo con escrituras |
| C | **Fuera de MCP**: ciclo de vida de módulos (DDL + revisión humana), API keys (secreto único), settings `is_secret`, borrado de dinero |
| D | **`users_update` con `role`** incluido, protegido por `roles:assign` (el usuario decide al crear la clave) |
| E | **Idempotencia**: `id` UUID generado por el cliente en `create` + `idempotency_key` para acciones repetibles; mismo patrón en REST |
| F | **Streamable HTTP stateless**, SDK oficial v2, versión de protocolo declarada |
| G | **API keys en v1**, OAuth 2.1 diferido con desviación documentada |
| H | **Contrato verificado**: `inputSchema`/`outputSchema` = schemas zod compartidos; el SDK valida la salida |
| I | **Errores**: JSON-RPC con `data.code` del ADR 0007; 401/403/404/429/500 |
| J | **Rate limiting** por clave y endpoint (30 req/min por defecto) + auditoría por tool |
| K | **`mcp_exposed`** por módulo (delta a task-01) para apagar sus tools sin desinstalar |
| L | **Palabras reservadas** de módulo (`admin`, `mcp`, `api`, `core`) — invariante del manifest (task-03) |

## 11. Criterios de aceptación

- Tres familias de endpoints (`/mcp`, `/mcp/admin`, `/mcp/<module_key>`) sobre Streamable HTTP stateless; cada una rechaza la clave del tipo incorrecto; módulo no disponible → `404`.
- El catálogo Core admite **acciones** (§4.1/§4.2) con sus scopes, y `tools/list` se filtra por lo que el llamador puede ejecutar.
- Las tools de módulo se exponen solo con módulo `active` + `mcp_exposed` + acceso del usuario + scope de la clave.
- `outputSchema`/`structuredContent` son los schemas y la representación compartidos; el SDK valida.
- Las escrituras son **idempotentes** por `id` de cliente o `idempotency_key`; un reintento no duplica.
- Los errores devuelven `data.code` del ADR 0007 sin filtrar internos; 401/403/404/429 correctos.
- Cada llamada suma a `audit` por tool y respeta el rate limit por clave/endpoint.
- Coherente con api-v1 §3.8 (delta), spec de tokens §3/§5, ADR 0004/0007, task-01/02/03.
- Aprobada por el usuario y revisada por segundo agente (DoD de Docs).
