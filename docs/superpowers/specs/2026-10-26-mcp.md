# Spec — Core: MCP del Core y por módulo (sprint 04, task 05)

**Fecha:** 2026-10-26
**Estado:** Borrador para aprobación del usuario
**Base:** [spec de API v1 §3.8](2026-10-25-api-v1.md) (**delta 2026-10-26**) · [ADR 0004](../../adr/0004-bordes-y-capa-de-aplicacion.md) (mismos casos de uso, representación compartida) · [spec de tokens §3/§5](2026-10-25-token-model.md) (**delta 2026-10-26**: MCP admin = clave de instancia, MCP usuario/módulo = clave delegada) · [ADR 0007](../../adr/0007-manejo-de-errores.md) (códigos de error) · [spec de datos](2026-10-26-core-data-model.md) (task-01: `api_keys.role_cap`, `profiles.deactivated_at`, `idempotency_keys`, `mcp_exposed`) · [spec de API del Core](2026-10-26-core-api.md) (task-02) · [spec de módulos](2026-10-26-modulo-system.md) (task-03: `mcp_tools`)
**Decide el usuario:** MCP por módulo + generales; MCP con acciones; idempotencia por id de cliente; `users_update`/rol; API keys v1 y OAuth en backlog (2026-10-26)
**Protocolo:** MCP `2026-07-28` (`_meta` por request, `server/discover`, Streamable HTTP) · SDK **v2** (`@modelcontextprotocol/server`)

## 1. Objetivo

Exponer la instancia a **agentes de IA** por **MCP**, con el **mismo backbone** que REST (mismos casos de uso, misma representación compartida — ADR 0004 §7) y con **capacidad de actuar**: invitar, gestionar usuarios y categorías, conceder acceso a módulos y escribir datos de los módulos.

**Límite de alcance:** aquí se fija transporte, topología, autenticación, catálogo del Core, contrato de tools de módulo, errores, idempotencia y operación. Las **tools concretas de cada módulo** son de la spec del módulo.

## 2. Topología: un MCP por módulo + generales

| Endpoint | Clave | Tools | Notas |
|---|---|---|---|
| **`/mcp`** | delegada `027_usr_…` | `profile_get`, `profile_update`, `instance_get`, `my_modules_list` | el "general" del usuario; `my_modules_list` es el **descubrimiento** de módulos conectables |
| **`/mcp/admin`** | instancia `027_svc_…` (con `role_cap`) | catálogo de administración (§4.1) | el "general" del admin |
| **`/mcp/<module_key>`** | delegada `027_usr_…` | **solo las tools de ese módulo** | requiere módulo `active` + `mcp_exposed` ≠ `none` + `has_module_access` + scope |

**Reglas**:
- **Identidad de tool = `(endpoint, tool)`**: ningún nombre se repite con semánticas distintas entre endpoints (`instance_get` vive solo en `/mcp`; `my_modules_list` ≠ `modules_list`). La auditoría registra `<endpoint>.<tool>` (p. ej. `admin.invitations_create`, `split-expenses.expenses_create`).
- **Cada ruta exige el tipo de clave correcto**: clave válida del tipo incorrecto → **403** (autenticada pero no autorizada, ADR 0007 §3), no 401.
- **Palabras reservadas**: un módulo no puede llamarse `admin`, `mcp`, `api` ni `core` (invariante del manifest, task-03 §3).
- **Ventajas**: `tools/list` corto (mejor selección del modelo), permiso en la URL, configuración independiente por agente en el cliente MCP, ciclo de vida limpio (`404` si el módulo no está disponible), rate limiting y auditoría por endpoint.

## 3. Transporte y cumplimiento de protocolo (`2026-07-28`)

- **Streamable HTTP**, era **moderna (`2026-07-28`)**: **no hay handshake `initialize`**; cada petición lleva `_meta` (`protocolVersion`, `clientInfo`, `clientCapabilities`) y los headers **`MCP-Protocol-Version`**, **`Mcp-Method`**, `Mcp-Name` cuando aplique.
- **`server/discover` es obligatorio** (MUST de la spec): declara `capabilities.tools` y el resto de capacidades. **No** se anuncian `resources`, `prompts` ni `sampling` (v1 expone solo tools); `listChanged: false`.
- **SDK v2**: paquete **`@modelcontextprotocol/server`**, con **versión exacta fijada (pin) en el plan y en el lockfile** (cadena de suministro). `McpServer` + `registerTool` + **`createMcpHandler(factory)`** con **una instancia por request** (sin sesiones, sin `sessionIdGenerator` — eso es API de la v1 del SDK).
- **Modo de era**: `legacy: 'reject'` (solo `2026-07-28`); si se quisiera compatibilidad con clientes antiguos, se documentaría el modo dual antes de activarlo.
- **Validación de `Origin` y `Host`** (DNS rebinding; MUST de la spec). `401` siempre con **`WWW-Authenticate`**.
- Solo `POST` (stateless). **Fuera de `/api/v1`**: MCP es JSON-RPC sobre HTTP, no un recurso REST (decisión consciente frente al API-first).
- **Versión de protocolo no soportada** → `-32022`; **header mismatch** → `-32020`.

## 4. Catálogo de tools del Core

### 4.1 `/mcp/admin` — acciones (MCP actúa, no solo consulta)

Todas las tools exigen `role_cap` suficiente (task-01: `api_keys.role_cap` ∈ `admin`|`super_admin`): el permiso efectivo es **`min(scopes de la clave, role_cap)`**.

| Tool | Acción | Scopes | `role_cap` mín. |
|---|---|---|---|
| `invitations_create` | crear invitación (email, nombre, `user_category_id`, módulos). **H3**: la respuesta **no incluye el token/enlace** de canje (secreto de un solo uso); se entrega fuera de MCP | `invitations:write` | admin |
| `invitations_list` | listar invitaciones (estado) | `invitations:read` | admin |
| `invitations_revoke` | revocar invitación | `invitations:write` | admin |
| `users_list` | listar usuarios (filtros `q`, `module`, `category`) — **sin email** en la salida. **Trade-off aceptado (H8)**: `q` puede buscar por email y confirmar existencia a un actor que ya es admin con `users:read` | `users:read` | admin |
| `users_get` | detalle de usuario (sin email) | `users:read` | admin |
| `users_update` | editar **solo perfil**: `display_name`, `locale`, `timezone` | `users:write` | admin |
| `users_assign_role` | cambiar `role` (`admin`↔`user`; `super_admin` solo con cap `super_admin`). **Invariantes (H2)**: el **root de `/setup` no se demota** y **siempre queda ≥1 `super_admin` activo**; violarlos → error de dominio, sin revelar cuál | `roles:assign` | admin (a `super_admin`: cap `super_admin`) |
| `users_deactivate` | desactivar usuario (soft; emite `user.deactivated` → hooks). **H2**: el **root no se desactiva** y no puede dejar la instancia sin `super_admin` activo | `users:deactivate` | **super_admin** |
| `categories_list` | listar categorías (+ `member_count`) | `user_categories:read` | admin |
| `categories_create` | crear categoría | `user_categories:write` | admin |
| `categories_update` | renombrar categoría | `user_categories:write` | admin |
| `categories_delete` | borrar categoría (**no** revoca concesiones materializadas) | `user_categories:write` | admin |
| `categories_add_member` | añadir usuario a categoría | `user_categories:write` | admin |
| `categories_remove_member` | quitar usuario de categoría | `user_categories:write` | admin |
| `categories_assign_module` | dar módulo a una categoría (**materializa**; **upsert** que limpia `revoked_at`) | `user_categories:write` + `modules:grant` | admin |
| `categories_unassign_module` | quitar el módulo de la **plantilla** de la categoría (no revoca concesiones) | `user_categories:write` + `modules:grant` | admin |
| `modules_list` | catálogo (estado, `is_public`, `mcp_exposed`) | `modules:read` | admin |
| `modules_grant` | conceder acceso a un módulo a un usuario | `modules:grant` | admin |
| `modules_revoke` | revocar acceso a un usuario (soft; re-grant lo restablece) | `modules:grant` | admin |
| `settings_get` | leer settings **con `mcp_access` ≥ read** | `settings:read` | admin |
| `settings_update` | escribir settings **con `mcp_access = write`** | `settings:write` | admin |
| `admin_actions_list` | log de mutaciones sensibles | `admin_actions:read` | **super_admin** |

### 4.2 `/mcp` — Core de usuario

| Tool | Acción | Scopes |
|---|---|---|
| `profile_get` | mi perfil | `profile:read` |
| `profile_update` | editar `display_name`, `locale`, `timezone` (**nunca** `role`) | `profile:write` |
| `instance_get` | metadatos no sensibles (equivalente al `/instance` público) | **sin scope** (basta con clave válida) |
| `my_modules_list` | **mis** módulos conectables: `active` + `mcp_exposed` ≠ `none` + acceso; admins → todos | **sin scope** (derivado, como `/me/modules`) |

### 4.3 `/mcp/<module_key>` — tools del módulo

- Solo las tools del manifest (`mcp_tools`) de **ese** módulo; **el nombre en el wire es el corto** (`expenses_create`), la auditoría lo registra como `<module_key>.<tool>`.
- Gates **reevaluados en cada `tools/call`** (no se confía en `tools/list`): módulo `active` + `mcp_exposed` (`read` admite tools de lectura; `read_write` también escrituras) + `has_module_access` + scope (`min(scopes de la clave, permisos del usuario)`).
- **Lectura vs escritura**: cada tool declara `kind: read|write` en el manifest. Con `mcp_exposed = read`, las de escritura **no** aparecen ni se pueden invocar.
- Escrituras pasan por el mismo caso de uso, validación zod y transacción que el REST; las mutaciones sensibles → `admin_actions`.
- Tool oculta o inexistente → **misma respuesta** (error de tool desconocida), sin enumeración.

### 4.4 Fuera de MCP (v1)

| Excluido | Motivo |
|---|---|
| **Ciclo de vida de módulos** (install/activate/deactivate/uninstall) | ejecuta DDL y exige revisión humana del diff (task-03 D) |
| **API keys** (crear/revocar) | secreto mostrado una sola vez (tokens §6); se gestiona en el panel |
| **Settings con `mcp_access = none`** (por defecto `security.*`, `connectivity.*`, `auth.*`) | pueden desactivar el rate limiting o ampliar CORS — **no** se exponen a agentes |
| **Settings `is_secret`** (SMTP, service account, BYOK) | un agente no lee ni escribe secretos |
| **`devices`, `currencies`, `translations`, `audit`** | dispositivos y tokens no se gestionan por agente; monedas/traducciones son de instalación; `audit` ya se consulta en el panel |
| **Borrado destructivo de datos de dinero** | lo decide el módulo; el dinero no se borra (spec §12) |

## 5. Idempotencia de las escrituras

Un agente puede **reintentar**; un reintento no puede duplicar ni "replayar" con otros argumentos.

- **`create` con id natural**: el cliente envía el **`id` UUID**; mismo `id` + mismo contenido → **mismo recurso**; mismo `id` + contenido distinto → **`conflict`**.
- **Acciones repetibles o sin id natural**: campo `idempotency_key` (obligatorio en las tools marcadas `idempotentHint: false` que mutan).
- **Registro**: tabla **`idempotency_keys`** (task-01) — `(api_key_id, endpoint, tool, key)` único, con **`request_hash`**, `state` (`pending`|`done`), respuesta **no sensible**, `expires_at` (TTL 24 h configurable). Se escribe **en la misma transacción** que la mutación.
- **Reglas**:
  - mismo `request_hash` → se devuelve el resultado guardado (**replay**);
  - `request_hash` distinto → **`conflict`** (nunca replay silencioso);
  - `pending` concurrente (misma clave en vuelo) → `conflict` con `retry_after`;
  - **nunca** se guardan secretos en la respuesta cacheada (un token de invitación no se persiste; el replay devuelve "ya creada" sin secreto);
  - el `id` de otro usuario responde **sin enumerar** (mismo error que inexistente);
  - el **replay devuelve el resultado de aquella mutación**, no el estado actual de la entidad (H11); el registro se purga por job (task-07) y una clave con `idempotency_key` únicos no puede llenar la tabla sin límite (TTL).
- **Mismo patrón en REST**: el contrato de idempotencia no depende del transporte (delta a task-02).

## 6. Contrato de entrada/salida

- **`inputSchema`**: el schema zod de entrada del caso de uso/endpoint, **`.strict()`** (rechaza campos no declarados → evita mass-assignment). La validación se hace **con el zod compartido dentro del wrapper** de la tool, para devolver `validation_failed` con `details` (no el error genérico del SDK).
- **`outputSchema`**: schema zod del recurso **o** de los envoltorios:
  - `ListResult<T>` = `{ data: T[], meta }` (listados);
  - `MutationResult` = `{ ok: true, resource?: T }` (mutaciones sin recurso propio);
  - `Instance` (metadatos de instancia).
  Los schemas deben ser **JSON-Schema-friendly** (sin `.transform()` que cambie la forma); el SDK valida la salida y un test compara el JSON Schema derivado con el zod.
- **`structuredContent`**: la representación compartida (ADR 0004 §7), idéntica al REST y al `resource` de eventos (task-04).
- **`content`**: incluye el **JSON serializado** de `structuredContent` como `TextContent` (recomendación de la spec) + un resumen en inglés; el servidor no localiza (ADR 0007 §1).
- **Paginación**: `offset`/`limit`/`cursor` del contrato v1; `meta` en `structuredContent`.
- **`tools/list` determinista** (orden estable) y filtrado por lo que el llamador puede ejecutar.

## 7. Errores (dos canales, spec `2026-07-28`)

**Canal 1 — errores de protocolo (error JSON-RPC)**:

| Situación | Respuesta |
|---|---|
| JSON malformado / request inválido | `-32700` / `-32600` |
| Método o tool desconocida (incluida tool oculta) | `-32601` / error estándar de tool desconocida |
| Versión de protocolo no soportada | `-32022` |
| Header mismatch (`Mcp-Method`/`Mcp-Name`) | `-32020` |
| Clave ausente, inválida, revocada o caducada | **HTTP 401** + `WWW-Authenticate` |
| Tipo de clave incorrecto para el endpoint, o scope de endpoint insuficiente | **HTTP 403** |
| Módulo no disponible (cualquier causa) | **HTTP 404** uniforme |
| Rate limit | **HTTP 429** + `Retry-After` (segundos) |
| Fallo inesperado del servidor | `-32603` / HTTP 500 |

> No se usan códigos del rango **legacy** (`-32000…-32099`).

**Canal 2 — errores de ejecución de tool** (la tool existe y se autorizó):

```json
{ "content": [ { "type": "text", "text": "{\"error\":{…}}" } ],
  "structuredContent": { "error": { "code": "validation_failed", "message": "…",
                                    "details": [ … ], "request_id": "…" } },
  "isError": true }
```

- `code` = código estable del ADR 0007 (`validation_failed`, `not_found`, `insufficient_scope`, `conflict`, `rate_limited`, `internal`…).
- `details` solo en `validation_failed` (campos y reglas).
- **`request_id`** en **todos** los canales (ADR 0007 §6), para soporte y correlación con logs.
- **Nunca** stack, SQL, rutas internas ni secretos, ni en dev (ADR 0007 §5).

**No enumeración**: módulo no disponible → 404 con el **mismo cuerpo** para "no existe", "desactivado", "no expuesto" y "sin acceso"; el motivo se registra solo server-side.

## 8. Operación: rate limiting, auditoría, anotaciones

- **Rate limiting** (delta a task-02): **tope global por clave (30 req/min)** + **sub-tope por endpoint** + **presupuesto de escritura separado y menor (10 req/min)**. Exceso → 429 + `Retry-After` en segundos. Configurable (`security.rate_limit.*`).
- **Auditoría**: cada llamada incrementa `audit` (`api_key_id` × `<endpoint>.<tool>`, ventana agregada — tokens §6). Nunca el token.
- **`admin_actions`**: mutaciones sensibles (invitar, cambiar rol, conceder acceso, settings) **dentro de la transacción**; `api_key_id` como actor cuando la llamada viene de una clave (task-01: actor humano o clave, nunca un perfil sintético).
- **Anotaciones obligatorias por tool**: `readOnlyHint`, `destructiveHint`, `idempotentHint` (el cliente las usa para pedir confirmación). Las tools `destructiveHint: true` exigen **`confirm: true`** en la entrada y devuelven `validation_failed` si falta.
  **Semántica (H9)**: `confirm: true` es un **requisito de entrada**, no una prueba de consentimiento humano — un agente puede enviarlo siempre. La garantía humana real reside en el **cliente MCP**, que decide si consulta al usuario a partir de `destructiveHint`.

## 8bis. Autenticación y desviación de OAuth

- `Authorization: Bearer <clave>` — claves del modelo de tokens aprobado (opacas, hasheadas, revocación instantánea, expiración opcional).
- **`/mcp/admin`** → clave **service** (`027_svc_`) con **`role_cap`** (task-01); permiso efectivo `min(scopes, role_cap)`.
- **`/mcp` y `/mcp/<module_key>`** → clave **delegada** (`027_usr_`); permiso efectivo `min(scopes, permisos del usuario)` + `has_module_access`.
- **Una clave service nunca actúa como usuario**; una delegada nunca entra en `/mcp/admin` (403).
- **Desviación documentada (OAuth)**: la spec MCP `2026-07-28` declara la autorización **OPTIONAL** y permite **autenticación propia** (HTTP SHOULD). Usamos API keys porque la instancia es autoalojada y privada, las emite su propio administrador y el modelo de tokens ya cubre revocación y scopes finos. **OAuth 2.1 + Client ID Metadata Documents** quedan en backlog (`docs/tasks/sprint-mcp-oauth/task-01.md`).
- **Revocación (H1)**: `revoked_at`/`expires_at` se comprueban **en BD en cada petición** (o la caché del token se invalida al revocar/expirar) — una clave revocada deja de funcionar en la llamada siguiente.
- Sin secretos en logs ni respuestas.

## 11. Testing (matriz obligatoria)

| Bloque | Casos |
|---|---|
| Tipo de clave × endpoint | delegada en `/mcp/admin` → 403; service en `/mcp` y `/mcp/<m>` → 403; clave revocada → 401 |
| Gates de módulo | `none`/`read`/`read_write`; `has_module_access`; scope; **reevaluación entre dos llamadas** (desactivar/revocar a mitad) |
| No enumeración | módulo inexistente = desactivado = no expuesto = sin acceso → mismo 404 y mismo cuerpo |
| Contrato | `outputSchema` derivado == zod; `structuredContent` == representación REST (test cruzado por tool) |
| Idempotencia | mismo payload → replay; payload distinto → `conflict`; otra clave; TTL; concurrencia; `id` de otro usuario sin enumerar |
| Errores | `isError` con `code`+`request_id`; sin stack/SQL/rutas; `-32020`/`-32022`/`-32601` |
| Seguridad | `settings_update` no toca `security.*`/`connectivity.*`; `users_assign_role` a `super_admin` exige `role_cap`; destructivas sin `confirm` → `validation_failed`; **desactivar/demotar el root → rechazo**; **dejar la instancia sin `super_admin` activo → rechazo**; `invitations_create` **no** devuelve token |
| Revocación (H1) | revocar la clave entre dos llamadas MCP → la siguiente es **401** |
| Idempotencia (H5/H6) | colisión por sesión (índice parcial); payload equivalente con distinto orden de claves → **replay**, no `conflict` |
| Operación | rate limit global/por endpoint/escritura; `audit` por `(endpoint, tool)` |
| Protocolo | `server/discover`, `_meta`, headers, `Origin` rechazado, `WWW-Authenticate` en 401 |

**CI**: check mecánico que compara `mcp_tools` del manifest con las tools registradas (nombres únicos, `kind`, `scopes` declarados, descripciones en inglés) — job `admin` (task-03 §6).

## 12. Criterios de aceptación

- Tres familias de endpoints sobre `2026-07-28` (Streamable HTTP, `_meta`, `server/discover`, headers, `Origin`), SDK v2, `legacy: 'reject'`.
- Catálogo Core con **acciones** y `role_cap`; 403 con clave del tipo incorrecto; 404 uniforme; 401 solo por credencial.
- `mcp_exposed` en 3 niveles con `read` por defecto; gates reevaluados por llamada.
- `outputSchema`/`structuredContent` compartidos y validados; `content` con el JSON.
- Escrituras idempotentes con `request_hash`; payload distinto → `conflict`.
- Errores en dos canales con `request_id` y sin internos; sin códigos legacy.
- Rate limiting (global + endpoint + escritura) y auditoría por `(endpoint, tool)`; destructivas con `confirm`.
- Coherente con api-v1 (delta), tokens §3/§5 (delta), ADR 0004/0007, task-01/02/03.
- Aprobada por el usuario, revisada por segundo agente y **auditoría de seguridad OWASP** (DoD de Docs punto 4) — veredicto `APROBADA CON OBSERVACIONES` (2026-10-26), sin hallazgos críticos ni altos, con H1–H7 resueltas en esta spec.
