## 1. Problema

La familia reparte gastos en hojas de cálculo, en el chat o en Splitwise. Splitwise funciona,
pero mete anuncios y paywalls en lo básico, obliga a una cuenta y no es parte del producto. La
spec de diseño ya define «gastos compartidos» como el primer módulo real, y la landing lo
anuncia como `planned`.

Además, el runtime de módulos existe pero **nunca se ha ejercitado con un módulo real**. OweNo
es el primer módulo que instala tablas, RLS, scopes, páginas de panel, widgets, canales y
eventos. Si algo del contrato no encaja, tiene que fallar aquí y no en el módulo siguiente.

## 2. Objetivo

Que un grupo de la familia pueda crear un grupo, invitar a sus miembros, apuntar un gasto con
reparto igual o importes exactos, ver quién debe a quién y liquidar con el **mínimo número de
pagos**, desde la app y desde el panel, sin depender de un servicio externo. Y que pueda traer
su historial de Splitwise una vez, sin rehacerlo a mano.

## 3. Alcance v1

**Dentro**
- Grupos con nombre, moneda y estado; categorías por grupo; **movimientos** (gastos y pagos)
  con pagador y reparto; balances; historial; **editar y eliminar** con baja lógica (D19).
- **Ciclo de vida (D15)**: cualquier usuario crea un grupo desde la app y los admins también
  desde el panel; el **creador invita** y el invitado **acepta o rechaza**; el creador puede
  **echar** y **bloquear**; cualquiera puede **salir**; el historial **nunca se borra**.
- **Salir exige saldo cero** (D3.9). El creador sí puede echar a alguien con saldo, con aviso:
  la deuda queda pendiente en el historial y el que se va deja de verla.
- Miembros **ficticios** (sin cuenta) para gastos históricos o para quien no se registra;
  enlace manual de un ficticio con una cuenta **solo por un admin**, sin claiming automático.
- **Borrado definitivo de un usuario (D16)**: su miembro pasa a ficticio conservando nombre e
  historial; ninguna pantalla lee `profiles` para nombrar a nadie.
- **Reparto**: a partes iguales o **importe exacto por persona** (D3.5), **solo entre los
  participantes elegidos en ese gasto** (D17): en un grupo de cinco, tres helados se dividen
  entre tres, no entre cinco. El pagador puede no participar.
- **Liquidación**: mínimo exacto de transferencias hasta el tope configurable
  `settlement_exact_limit` (4–20, defecto 12), voraz con aviso por encima (D3.6, D3.7).
- **Importador de Splitwise** en la app para el creador del grupo: CSV por grupo, preview,
  mapeo y commit (D3.2, D3.4).
- Panel: `overview` y `groups`; configuración del módulo con el deslizador del tope.
- Realtime y push por el runtime del Core (D13): canal por grupo, eventos de gasto,
  pago y enlace de miembro.

**Fuera**
- Presupuestos, fotos de recibo, OCR, recurrencia y sincronización bancaria (D3.8).
- Multi-divisa: se **rechaza** el archivo con aviso (D3.3).
- Porcentajes y pesos en el reparto.
- Claiming automático de ficticios.
- Pantallas Android (tarea 07). Aquí solo se diseñan en F1.
- Sección «App» en el panel (D9).
- Cualquier envío de email del módulo: el correo es del Core.

## 5. Modelo de datos

Esquema `module_owe_no`, todas las tablas con RLS y `group_id` salvo las participaciones (que lo
heredan del gasto).

### 5.1 Tablas

```sql
-- Grupos
owe_no_groups(id uuid pk, name text not null, currency char(3) not null,
              archived_at timestamptz, created_by uuid null references profiles(id) on delete set null,
              created_at, updated_at)

-- Miembros (registrados o ficticios; el tipo se deriva de user_id)
owe_no_members(id uuid pk, group_id uuid not null references owe_no_groups(id) on delete cascade,
               user_id uuid null references profiles(id) on delete set null,
               display_name text not null,
               state text not null check (state in ('invited','active','left','removed')),
               invited_by uuid null references profiles(id) on delete set null,
               invited_at timestamptz null, joined_at timestamptz null, left_at timestamptz null,
               created_at, updated_at,
               unique (group_id, user_id) deferrable initially deferred)

-- Bloqueos: un bloqueado no se puede invitar ni reactivar
owe_no_blocks(id uuid pk, group_id uuid not null, user_id uuid not null references profiles(id) on delete cascade,
              blocked_by uuid null references profiles(id) on delete set null, created_at,
              unique (group_id, user_id))

owe_no_categories(id uuid pk, group_id uuid not null, name text not null,
                  color_slot text not null, created_at, updated_at)

-- Un solo tipo de hecho: dinero que se mueve. Gasto y pago cambian la dirección, no la entidad.
owe_no_movements(id uuid pk, group_id uuid not null,
                 kind text not null check (kind in ('expense','settlement')),
                 description text not null,
                 amount_minor bigint not null check (amount_minor > 0),
                 currency char(3) not null,
                 paid_by_member_id uuid not null references owe_no_members(id),
                 category_id uuid null references owe_no_categories(id) on delete set null,
                 occurred_on date not null,
                 created_by uuid null references profiles(id) on delete set null,
                 updated_by uuid null references profiles(id) on delete set null,
                 deleted_at timestamptz null,
                 deleted_by uuid null references profiles(id) on delete set null,
                 created_at, updated_at)

owe_no_movement_shares(movement_id uuid not null references owe_no_movements(id) on delete cascade,
                       member_id uuid not null references owe_no_members(id),
                       amount_minor bigint not null check (amount_minor >= 0),
                       primary key (movement_id, member_id))
```

Índices: `owe_no_members(group_id, state)`,
`owe_no_movements(group_id, occurred_on desc) where deleted_at is null`,
`owe_no_movement_shares(member_id)`.

**Por qué una sola tabla.** Un gasto y un pago son el mismo hecho con distinto sentido: alguien
pone dinero y otros se benefician. Un **gasto** reparte el importe entre `k` participantes; una
**liquidación** (`settlement`) es una devolución de deuda entre dos personas y tiene
**exactamente una participación**, el miembro que recibe, por el importe completo (y el pagador no
puede ser el receptor). Así hay un historial, una política de RLS, un camino de edición y uno de
importación, en vez de dos casi iguales.

**«Pago» significa dos cosas y no se confunden.** «Yo pago la compra» es un **gasto**: el pagador
puede participar o no, y el movimiento tiene una o varias participaciones. «Dani me paga lo que
me debe» es una **liquidación**: pagador Dani, una participación (yo), importe completo. Un mismo
hecho nunca es las dos cosas:

| Caso | `kind` | Pagador | Participaciones |
|---|---|---|---|
| Ana paga la compra y participa con Luis | `expense` | Ana | Ana 50 %, Luis 50 % |
| Ana paga la compra y no participa | `expense` | Ana | Luis 100 % |
| Luis devuelve su mitad a Ana | `settlement` | Luis | Ana 100 % |
| Luis y Marta pagan a la vez lo que deben | 2 × `settlement` | Luis / Marta | Ana 100 % cada uno |

**El número de participaciones no decide el `kind`.** Un gasto comprado solo para Luis (una
participación) y una devolución de Luis (una participación) se parecen en los balances, pero uno
es gasto y el otro es pago: cambia el historial, los informes y la importación. Por eso `kind` es
explícito y nunca se infiere.

### 5.2 Invariantes

1. La suma de `owe_no_movement_shares` de un movimiento **es** `owe_no_movements.amount_minor`.
   Se comprueba en el caso de uso y en un test; no se confía solo en el cliente.
1bis. Un movimiento tiene **al menos una participación**; en un `expense` son un subconjunto de
   los miembros `active` y no tienen por qué incluir al pagador. En un `settlement` hay
   **exactamente una**, es el receptor y no es el pagador, y su importe es el total.
2. Un miembro `invited` **no** es pagador ni participación de ningún gasto; al aceptar pasa a
   `active` y solo entonces puede aparecer.
3. La moneda de un gasto es la del grupo; el importador rechaza cualquier otra.
4. Todo `user_id` no nulo de un miembro `active` es único por grupo (un usuario no está dos
   veces en el mismo grupo).
5. Un miembro `left` o `removed` no puede ser pagador, ni participación, ni receptor de una
   movimiento nuevo; el historial anterior se conserva.
6. `display_name` es una **copia** y no se actualiza desde `profiles`: si el usuario cambia de
   nombre, el historial conserva el nombre con el que ocurrió, y si se borra, el miembro sigue
   teniendo nombre.

### 5.3 Tipo derivado y borrado

`kind` **no** es una columna: se calcula como `user_id is null ? 'fictitious' : 'user'`. Así el
borrado definitivo (`purgeUser` → `delete from auth.users`) deja el miembro como ficticio por la
propia FK, sin escrituras adicionales y sin depender de un hook.

### 5.4 RLS

Todas las tablas con `enable row level security` y políticas por membresía, usando el helper de
identidad de la tarea 02 (el DDL no puede escribir `auth.uid()`).

- **Lectura del grupo**: miembro con estado `invited` o `active`. La invitación necesita el
  nombre y la moneda del grupo para mostrarse.
- **Lectura de movimientos, participaciones, categorías y balances**: solo `active`.
- **Escritura de movimientos y categorías**: solo `active`; el creador no tiene trato
  especial para escribir gastos (cualquier miembro activo apunta gastos).
- **Escritura de miembros, bloqueos y edición del grupo**: solo el **creador** (`owe_no_groups.created_by`)
  y los admins de la instancia desde el panel.
- **Salir**: el propio miembro `active` puede pasar a `left` si su balance es cero; la
  comprobación de saldo se hace en el caso de uso dentro de la misma transacción.
- Un `invited` no puede leer gastos ni balances: el detalle le devuelve el grupo sin cifras y la
  tarjeta de invitación.
- Los tests de aislamiento cubren, para cada estado, lectura y escritura desde otro grupo.

### 5.5 Dinero y fechas

- Importes en **enteros de céntimos** (`amount_minor`), nunca `float`; agregaciones con
  `bigint`.
- `spent_on` y `settled_on` son `date` de calendario, no instantes; no se convierten de zona
  horaria (ADR 0008).
- Moneda por grupo en formato ISO 4217; la instancia aporta la de por defecto.

## 6. Dominio

### 6.1 Participantes del gasto

Un grupo puede tener `n` miembros y un gasto afectar solo a `k`, con `1 ≤ k ≤ n`. En el grupo
del viaje sois cinco, pero si solo tres compran helados, el importe se reparte **entre esos tres**.

- La app abre el alta de gasto con **todos los miembros activos seleccionados** y el usuario
  desmarca a quien no participa; hay atajos «Todos» y «Ninguno».
- `k = 0` no se permite: el botón de guardar queda deshabilitado y el servidor devuelve
  `validation_failed` (`code: no_participants`).
- **El pagador no tiene que participar.** Quien paga los helados puede no comerlos: se registra
  el pago completo y el reparto solo entre los que sí participan. El balance del pagador sube por
  el total y no baja por ninguna participación.
- Solo pueden participar miembros `active`; un `invited` no participa (no ve el gasto), y un
  `left`/`removed` tampoco.
- Los participantes son una decisión **por gasto**, no una propiedad del grupo: el siguiente
  gasto vuelve a proponer a todos.

### 6.2 Reparto igual

- `total = amount_minor`, `k` = número de participantes seleccionados.
- `base = total / k`, `rem = total % k`; las `rem` primeras participaciones (por id de miembro
  ascendente) reciben un céntimo más.
- La suma siempre es exacta. Test con `total % k != 0`, con `k = 1` y con `k = n`.
- Cambiar la selección recalcula el reparto: nunca queda una participación de alguien
  desmarcado.

### 6.3 Reparto exacto

- Solo aparecen los participantes seleccionados, cada uno con su importe editable.
- El servidor solo acepta si `sum(shares) == amount_minor`, cada `share >= 0` y el conjunto de
  `shares` coincide **exactamente** con los participantes del gasto; si no, `validation_failed`
  con el detalle por miembro.
- Se guarda tal cual: el modelo no distingue «igual» de «exacto». La UI sugiere el igual y deja
  corregir importes; eso es todo.

### 6.4 Balances

```
balance(member) = sum(movements.paid_by = member, deleted_at is null)   -- lo que puso
                - sum(shares.member = member, deleted_at is null)       -- lo que le tocó
```

Un gasto y un pago usan la misma fórmula: en un pago, la única participación es la del receptor,
así que el pagador suma el total y el receptor lo resta. No hay una segunda contabilidad.

- Invariante: la suma de balances de un grupo **es cero**. Test con gastos, pagos y
  miembros que salen.
- El balance de un `left`/`removed` sigue calculándose y se muestra al creador como **pendiente**;
  el que se fue no lo ve.

### 6.5 Liquidación con el mínimo exacto

Entrada: lista de balances no nulos, `m` miembros, suma cero. Salida: transferencias
`{from, to, amount_minor}`.

**Algoritmo (exacto).** Búsqueda con retroceso sobre los saldos, en el orden canónico de
`member_id`:

1. Se toma el primer miembro con saldo distinto de cero.
2. Se prueba a saldarle **por completo** contra cada miembro de signo opuesto, en orden canónico.
3. Se recursa y se queda el mínimo de transferencias; empate → la primera solución en el orden
   canónico (determinismo).
4. Poda: si el número de transferencias ya iguala la mejor encontrada, se corta; los saldos
   repetidos se agrupan para no repetir ramas equivalentes.

Es exacto porque en un óptimo el primer miembro puede saldarse con una sola contraparte (si su
deuda se reparte entre dos, se puede mover el importe de una a la otra sin aumentar el número de
transferencias).

**Límite y degradación.** Si `m > settlement_exact_limit` (setting del módulo, 4–20, defecto
12), se usa el **voraz**: acreedores y deudores ordenados por importe descendente y, a igualdad,
por `member_id`; se salda el mayor contra el mayor. La UI avisa: «Grupo grande: liquidación
simplificada» y muestra el tope configurado. El voraz también es determinista, pero **no** se
anuncia como mínimo.

**Garantías.**
- Determinismo: los mismos saldos producen las mismas transferencias, aunque cambie el orden de
  lectura de la base.
- Conservación: la suma de lo que paga cada deudor es su deuda, y la de cada acreedor su crédito.
- Test oráculo: para `m ≤ 6`, fuerza bruta sobre todas las agrupaciones de suma cero; el mínimo
  del algoritmo debe coincidir con el oráculo, y nunca ser menor.
- Test de tope: `m = 13` con el tope por defecto usa voraz y lo dice; con el tope en 20 usa el
  exacto.
- Sin dependencias externas: no hay paquete mantenido que resuelva el mínimo exacto (verificado
  2026-11-12: los repos existentes implementan el voraz).

### 6.6 Confirmar un pago

- `POST /groups/{id}/movements` con `kind: "settlement"` acepta `to_member_id` y
  `amount_minor`; el pagador es siempre el miembro del llamante (no se puede pagar en nombre de
  otro).
- El importe no puede superar el saldo pendiente entre ambos; si lo supera, `validation_failed`.
- Se puede pagar una parte: el balance restante se recalcula.
- Un pago se guarda como un movimiento con una sola participación (la del receptor).

### 6.7 Editar y eliminar movimientos

- **Quién**: el **autor** del movimiento o el **creador del grupo**. Nadie más, ni siquiera otro
  admin del panel (D9: el panel no toca dinero).
- **Qué se puede editar**: importe, descripción, fecha, categoría, pagador, participantes y sus
  importes. Si cambia el importe o los participantes, se recalculan las participaciones.
- **Cómo se elimina**: **baja lógica** (`deleted_at`, `deleted_by`). El movimiento desaparece del
  historial y de los balances, pero la fila y sus participaciones se conservan: no se rompe la
  auditoría ni la integridad. En v1 **no hay restaurar** desde la app; es una decisión de
  producto, no un olvido.
- **Efecto en balances**: se recalculan con la fórmula de §6.4. Un pago ya registrado **sigue
  ahí**: si editas o borras el gasto que lo motivó, el pago no se deshace solo. La app avisa en
  el borrado si hay pagos posteriores entre esas personas.
- **Auditoría mínima**: `updated_by`/`updated_at` y `deleted_by`/`deleted_at`; sin tabla de
  revisiones en v1.
- **Historial visible**: los movimientos eliminados no se muestran a los miembros. Un admin
  puede verlos en el panel como parte del historial técnico, pero **no editarlos ni restaurarlos**
  desde la UI.
- **Eventos**: `owe_no.movement_updated` y `owe_no.movement_deleted` con push a los demás
  miembros (nunca al autor), para que un cambio de balance no pase desapercibido.

### 6.8 Ciclo de vida de miembros

| Desde | Acción | A | Quién |
|---|---|---|---|
| — | invitar | `invited` | creador |
| `invited` | aceptar | `active` | el propio invitado |
| `invited` | rechazar | (se borra el miembro) | el propio invitado |
| `active` | salir | `left` | el propio miembro, **solo con balance cero** |
| `invited`/`active` | echar | `removed` | creador (con saldo, con aviso) |
| `active`/`left`/`removed` | bloquear | bloqueo + `removed` | creador |
| — | enlazar ficticio | `user_id` rellenado, historial intacto | admin |

- Rechazar una invitación **borra** el miembro solo si no tiene movimientos (no puede tenerlos:
  `invited` no participa). Es la única fila que se borra.
- Echar a alguien con saldo no borra nada; el creador ve «deuda pendiente» y el que se fue deja
  de ver el grupo.
- Un bloqueado no puede volver a ser invitado: el `POST` de invitación devuelve
  `validation_failed` con `code: blocked`.
- Salir estando en un grupo con saldo devuelve `validation_failed` con `code: balance_not_zero`
  y el importe pendiente.

### 6.9 Importador de Splitwise (CSV)

La UI vive en la app (tarea 07); el endpoint y el parser viven aquí.

**Formato aceptado (confirmado con un export real, 2026-11-13).** CSV con cabecera,
delimitador `,` o `;` (se detecta), UTF-8 con o sin BOM. **La cabecera va en el idioma de la
cuenta**: se aceptan alias ES y EN — `Fecha`/`Date`, `Descripción`/`Description`,
`Categoría`/`Category`, `Coste`/`Cost`, `Moneda`/`Currency`. `Categoría` es opcional. Una
columna por persona cuya **cabecera es el nombre** y cuyo valor es el impacto en el balance.
Si falta una columna obligatoria, el error nombra las que faltan. El fixture aprobado está en
[`fixtures/splitwise-demo.csv`](../../tasks/sprint-15-app-y-finanzas/fixtures/splitwise-demo.csv).

**Lectura por impacto, no por etiqueta.** Para cada fila se calcula el vector de impactos por
persona. La suma debe ser cero (±1 céntimo por redondeo del export, que se corrige en la
persona de mayor valor absoluto). De ahí salen pagador (`impacto = +importe`) y participaciones
(`-impacto`). Si el vector no cuadra, la fila es un error con número de línea y no se importa
nada.

**Pagos.** El marcador es la **categoría**: `Pago` (ES) o `Payment` (EN). Esas filas tienen
`+coste` en quien paga y `-coste` en quien recibe, y se importan como **pagos**
(`kind: settlement`). Si el marcador no aparece, una fila de dos personas entra como gasto:
**los balances son idénticos**, solo cambia el historial mostrado, así que un fallo de detección
no corrompe saldos.

**Filas irregulares (vistas en el export real).**
- Filas en blanco o con celdas de solo espacios: se **descartan** y se cuentan en el preview.
- Fila con `Coste` vacío pero impactos válidos (`+212.50/-212.50`): el importe se **deriva** de
  los impactos, se marca como derivado y no se rechaza.
- Impactos que no suman el coste (±1 céntimo): se corrige el céntimo en la persona de mayor
  valor absoluto; si la diferencia es mayor, la fila es un error con número de línea.

**Multi-divisa.** Si aparece más de una `Currency` distinta en el archivo, se **rechaza entero**
con `validation_failed`, `code: multi_currency` y la lista de divisas encontradas. No se convierte
nada.

**Fechas.** ISO `YYYY-MM-DD`. Cualquier otro formato que no sea inequívoco es error de fila con
número de línea.

**Importes.** El export real usa `.` como decimal y sin separador de miles. Se aceptan también
`,` solo si no hay ambigüedad: si una celda tiene ambos, el último es el decimal; si solo hay
comas y hay más de una, se interpretan como miles. Paréntesis = negativo. Fuera de eso, error.
Nunca `float`: se parsea a céntimos con enteros.

**Identidades.**
1. Autoenlace por **nombre exacto y único** contra: miembros del grupo (incluidos ficticios) y
   usuarios activos de la instancia. Si hay 0 o más de 1 coincidencia, no se autoenlaza.
2. Sin coincidencia: la app pide **vincular a un usuario activo** (selector id + nombre) o
   **crear un ficticio**. Nunca se pide email: el CSV no lo trae.
3. Dos nombres del CSV que el usuario vincula a la misma persona se **fusionan** en un miembro;
   el preview lo muestra antes de confirmar.
4. Un usuario registrado enlazado que **no** es miembro del grupo recibe **invitación** (D15);
   un ficticio no.
5. El commit nunca crea usuarios: solo miembros y, como mucho, invitaciones.

**Seguridad del archivo.**
- Tamaño máximo 2 MB y 5.000 filas; por encima, `validation_failed` con el límite.
- Ningún valor del CSV se evalúa: las celdas que empiezan por `=`, `+`, `-` o `@` se guardan
  como texto y se escapan al mostrarse (inyección de fórmulas).
- Sin fórmulas, sin macros, sin enlaces: es texto plano.
- El parser no toca la red ni ejecuta nada del archivo.

**Commit.**
- `preview` (dry-run) devuelve el recuento, los errores por línea, las identidades sin enlazar,
  las divisas y los duplicados; no escribe nada.
- `commit` inserta en **una transacción**: o entra todo, o no entra nada.
- **Deduplicación**: el CSV no trae `expense_id`; se calcula un hash por fila (fecha,
  descripción, importe, divisa e impactos ordenados) y se compara con las importaciones previas
  del grupo. Las filas ya importadas se listan y exigen `confirm_duplicates: true` para
  repetirlas.
- El resultado incluye `created`, `skipped_duplicates`, `errors` y `invitations_sent`.

## 7. API

Base `/api/v1`, envelope y errores de ADR 0007, zod en todos los bordes, idempotencia en
escrituras (`Idempotency-Key`) y rate limit.

| Método y ruta | Acción | Scope | Quién |
|---|---|---|---|
| `GET /owe-no/groups` | grupos donde soy miembro (`invited`/`active`), paginado | `expenses:read` | sesión |
| `POST /owe-no/groups` | crear grupo (creador = llamante, miembro `active`) | `expenses:read_write` | sesión |
| `GET /owe-no/groups/{id}` | detalle: grupo, miembros visibles, mi rol | `expenses:read` | miembro |
| `PATCH /owe-no/groups/{id}` | nombre, moneda, archivar | `expenses:read_write` | creador/admin |
| `GET /owe-no/groups/{id}/panel/members` | miembros y estado | `expenses:read` | miembro `active` |
| `POST /owe-no/groups/{id}/panel/members` | invitar por `user_id` | `expenses:read_write` | creador |
| `DELETE /owe-no/groups/{id}/panel/members/{memberId}` | echar | `expenses:read_write` | creador |
| `POST /owe-no/groups/{id}/panel/members/{memberId}/block` | bloquear | `expenses:read_write` | creador |
| `POST /owe-no/groups/{id}/panel/members/{memberId}/link` | enlazar ficticio a cuenta | `expenses:read_write` | admin |
| `POST /owe-no/groups/{id}/leave` | salir (exige saldo cero) | `expenses:read_write` | el propio miembro |
| `GET /owe-no/invitations` | invitaciones pendientes | `expenses:read` | sesión |
| `POST /owe-no/invitations/{id}/accept` | aceptar | `expenses:read_write` | el invitado |
| `POST /owe-no/invitations/{id}/decline` | rechazar | `expenses:read_write` | el invitado |
| `GET /owe-no/groups/{id}/panel/categories` | categorías | `expenses:read` | miembro `active` |
| `POST /owe-no/groups/{id}/panel/categories` | crear categoría | `expenses:read_write` | miembro `active` |
| `GET /owe-no/groups/{id}/movements` | historial (gastos y pagos), filtros y paginación | `expenses:read` | miembro `active` |
| `POST /owe-no/groups/{id}/movements` | alta de gasto (`kind: expense`) o pago (`kind: settlement`) | `expenses:read_write` | miembro `active` |
| `GET /owe-no/groups/{id}/movements/{movementId}` | detalle con participaciones | `expenses:read` | miembro `active` |
| `PATCH /owe-no/groups/{id}/movements/{movementId}` | editar un movimiento | `expenses:read_write` | autor o creador |
| `DELETE /owe-no/groups/{id}/movements/{movementId}` | baja lógica | `expenses:read_write` | autor o creador |
| `GET /owe-no/groups/{id}/balances` | balances y transferencias sugeridas | `balances:read` | miembro `active` |
| `POST /owe-no/imports/splitwise` | preview y commit del CSV | `expenses:read_write` | creador |
| `GET /owe-no/groups/{id}/linkable-users` | usuarios activos (id + nombre) | `expenses:read_write` | creador |
| `GET /owe-no/groups/{id}/imports` | historial de importaciones | `expenses:read_write` | creador |

Reglas transversales:

- Un `invited` recibe `403` en todo lo que no sea su grupo (nombre y moneda) y sus invitaciones.
- Un `left`/`removed` recibe `403` en todo el grupo, incluido `GET /groups/{id}`; su historial
  sigue en la base, pero no se sirve.
- Un recurso de otro grupo responde `404` uniforme, nunca `403` (no se filtra existencia).
- Las escrituras de dinero devuelven el recurso actualizado y, cuando aplica, los balances
  recalculados.
- Paginación por cursor o `limit`/`offset` con máximo 100; filtros `from`, `to`, `category_id`,
  `member_id`.
- Idempotencia: `POST` de movimiento e importación aceptan `Idempotency-Key`; repetir la misma
  clave devuelve el mismo recurso sin duplicar.
- `PATCH`/`DELETE` de un movimiento: el autor o el creador del grupo; cualquier otro recibe
  `403` (o `404` uniforme si no es miembro, para no filtrar existencia).

### 7.1 Formas de las respuestas

```jsonc
// GET /owe-no/groups/{id}
{ "group": { "id", "name", "currency", "archived_at", "created_by", "role": "creator|member|invited",
             "member_count", "my_balance_minor" },
  "members": [ { "id", "display_name", "kind": "user|fictitious", "state", "is_me" } ] }

// GET /owe-no/groups/{id}/balances
{ "balances": [ { "member_id", "display_name", "amount_minor" } ],
  "settlement": { "exact": true, "limit": 12, "transfers": [
     { "from_member_id", "to_member_id", "amount_minor" } ] },
  "pending": [ { "member_id", "display_name", "amount_minor" } ] }

// POST /owe-no/groups/{id}/movements
// kind: expense → participant_member_ids no vacío; shares se deriva si se omite (reparto igual)
// kind: settlement → to_member_id, una sola participación por el total
{ "movement": { "id", "kind": "expense|settlement", "description", "amount_minor", "currency",
                "occurred_on", "paid_by_member_id", "category_id",
                "participant_member_ids": ["..."],
                "shares": [ { "member_id", "amount_minor" } ] },
  "balances": [ ... ] }
```

`pending` son los saldos de miembros `left`/`removed`; solo los ve el creador.

## 10. App móvil (diseño en F1; implementación en la tarea 07)

### 10.1 Entrada y navegación

- **Al abrir OweNo se entra en su inicio** («Grupos»): cabecera del módulo, tarjeta de resumen y
  la lista de grupos. No se entra en un grupo concreto ni en un formulario.
- **Cabecera del módulo siempre visible** en todas sus pantallas: volver, **logo y nombre
  OweNo**, el contexto actual (grupo o sección) y un **⋯** con el menú del módulo. Así se sabe
  siempre en qué módulo se está, aunque el shell y el módulo compartan el mismo espacio.
- El **⋯** abre una hoja con: **Grupos**, **Invitaciones** (con contador), **Importar de
  Splitwise** (solo si eres creador de algún grupo) y **Ajustes del módulo**. «Volver a
  Módulos» cierra el módulo. Las acciones de administración (permisos, instalar) no están aquí:
  viven en el panel.
- **Volver** sube un nivel dentro del módulo (gasto → grupo → grupos); desde el **inicio del
  módulo** vuelve a Módulos del shell, no a Inicio, para no perder el contexto del lanzador.
- El **widget** de OweNo vive en el **Inicio del shell**; el inicio del módulo repite el resumen
  como tarjeta, no como un widget independiente.
- **Recordar la última ubicación (D18)**: el shell guarda `home`, `modules` o `module:<key>`
  cada vez que se navega a una de esas tres cosas. Al abrir la app con sesión válida, restaura
  esa ubicación y, si es un módulo, entra en **su pantalla raíz** (OweNo → Grupos). **Nunca**
  restaura una pantalla profunda ni un formulario a medias. Si el módulo ya no existe o no
  tengo acceso, cae en `modules`; si no hay ningún módulo, en `home`.

### 10.2 Pantallas

Dashboard con el widget de OweNo, inicio del módulo (grupos), detalle (balances, gastos,

- El grupo se elige dentro de OweNo; no hay selector global (el shell no cambia).

## 11. Seguridad

| Activo | Amenaza | Control |
|---|---|---|
| Gastos y balances de un grupo | IDOR entre grupos | RLS por membresía + guard + tests de acceso cruzado por estado; `404` uniforme. |
| Invitaciones | Invitar a quien no quieres, spam | Solo el creador invita; aceptación obligatoria; bloqueo por grupo; rate limit. |
| Ficticios | Suplantar a una persona | Enlace solo por admin; sin claiming; auditoría con `created_by`. |
| CSV | Inyección de fórmulas, archivo enorme, bombas de parseo | Límite de tamaño y filas, celdas escapadas, sin evaluación, timeouts, parseo en servidor. |
| CSV | Importar datos ajenos | Solo el creador del grupo destino; el commit no crea usuarios. |
| Dinero | Manipulación de importes | Enteros, invariantes en servidor, idempotencia, sin edición destructiva. |
| Salida del grupo | Deuda invisible | Salir exige saldo cero; echar con saldo deja la deuda visible al creador. |
| Settings | Rango abusivo del tope | Validación en servidor (4–20) y aviso al usuario. |
| Eventos | Fuga por canal | `core_can_subscribe` con la `members_fn` del grupo. |
