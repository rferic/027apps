# Spec — API pública v1: contrato estable y mecanismo de extensión

**Fecha:** 2026-10-25
**Estado:** Borrador para aprobación del usuario
**Base:** [spec de diseño §7](2026-10-24-027apps-design.md) (contrato OpenAPI, rate limiting, API keys con scopes) · [spec de tokens](2026-10-25-token-model.md) (API keys opacas instancia/delegado, expiración, rotación, scopes) · [spec de auth](2026-10-25-auth.md) (Supabase = identidad + transporte; móvil con JWT) · [ADR 0004](../../adr/0004-bordes-y-capa-de-aplicacion.md) (puertas delgadas, guard, zod en el borde, representación compartida) · [ADR 0006](../../adr/0006-realtime.md) (eventos de dominio con representación compartida) · [ADR 0007](../../adr/0007-manejo-de-errores.md) (envelope de errores) · [ADR 0008](../../adr/0008-fechas-y-moneda.md) (fechas/moneda, config de instancia)
**Decide el usuario:** puntos A–G de la conversación de diseño (2026-10-25)

## 1. Objetivo

Definir el **contrato estable** de la API pública v1 — la superficie única de datos para móvil y terceros (API-first obligatorio, spec §2/§7) — y el **mecanismo de extensión** por el que el Core y cada módulo añaden recursos al contrato sin tocar su mecánica.

**Límite de alcance:** esta spec **no cataloga el inventario de endpoints del Core**. El Core es una capacidad transversal que crece con el proyecto; su superficie inicial se diseña en el **sprint de diseño del Core** (`docs/tasks/sprint-core-design/`), sobre este contrato. Aquí solo se fija: (a) la mecánica estable del contrato y (b) el mínimo transversal de arranque que el propio contrato necesita.

## 2. Fronteras y principios

1. **API-first**: el móvil y terceros hablan **solo** con `/api/v1`; nunca con la BD (spec §7, ADR 0004).
2. **Casos de uso, no transporte**: cada endpoint es una **puerta delgada** que autentica, autoriza y valida (zod), y delega en el caso de uso orquestador (ADR 0004 §1–4). Ninguna regla de negocio en el handler.
3. **Representación compartida**: la salida es un **recurso** con forma explícita, producido por la capa de serialización compartida por todas las puertas (API, MCP, comandos) — ADR 0004 §7. El mismo recurso que viaja en los eventos realtime (ADR 0006).
4. **Contrato como fuente de verdad**: el **OpenAPI se genera** desde los schemas zod compartidos (A2) — nunca escrito a mano; el cliente Kotlin se genera del OpenAPI.

## 3. Contrato estable

### 3.1 Versionado (A1)

- URL con versión fija: **`/api/v1/...`**. Sin negociación por headers.
- Cambios incompatibles → nueva versión (`/v2`); la `v1` se mantiene el tiempo acordado. Cambios de `code` de error (ADR 0007) o de forma de recurso son breaking y siguen este mismo versionado.

### 3.2 Autenticación y autorización (B)

| Llamador | Credencial | Guard |
|---|---|---|
| App móvil | `Authorization: Bearer <JWT de Supabase Auth>` (auth spec §4) | Verifica JWT → identifica usuario → `authorize(caller, scopes)` (ADR 0004 §2) |
| Terceros | `Authorization: Bearer <API key 027_usr_/027_svc_>` (spec de tokens) | Resuelve la key opaca (solo hasheada en BD), vigencia/rotación → scopes → `authorize` |
| MCP | **API key de instancia** (`027_svc_`, spec de tokens §3.2; la taxonomía de tokens **no tiene un tipo `mcp`** — MCP/IA va con el token de instancia, sin identidad de usuario, con scopes por módulo) | Igual que terceros; herramientas con scopes por módulo (E) |

- **Scopes por acción expuesta** (ADR 0004 §2): cada puerta declara los scopes que exige (una acción puede requerir varios, p. ej. `users:create` + `permissions:assign`); el guard los comprueba. Para keys delegadas (`027_usr_`), acceso efectivo = `min(scopes del token, permisos del usuario)` (spec de tokens).
- **Permisos en vivo**: el lookup del token se cachea; la resolución de permisos (grupos, roles, módulos activos) se lee de BD por petición o con caché invalidada al cambiar membresía/rol (spec de tokens §5). RLS como segunda barrera (ADR 0004 §5).
- **Sin `pull_request_target` ni secreto en cliente**: las keys nunca llevan prefijo `NEXT_PUBLIC_`; el guard-secrets del CI lo vigila (cicd.md).

### 3.3 Rate limiting (C1)

- **Por identidad, en código, en la puerta** (en Vercel Free no se controlan limits por IP de plataforma). **Revisión expresa del «por token y por IP» de la spec de tokens §6**: queda fijado **por identidad** (token/usuario), sin límite por IP en v1 para superficies autenticadas (la spec de tokens §9 delega el rate limiting de terceros a esta spec).
  - **Delta 2026-10-26 (spec del Core, task-02):** los endpoints **sin identidad** (`/health`, `/instance`, `/invitations/{token}/redeem`) no pueden rate-limiting por usuario, así que reciben un **límite propio por IP/token** (p. ej. 30 req/min) — desviación registrada, ver `2026-10-26-core-api.md` §4.
- Umbrales diferenciados por tipo de llamador (a calibrar en el Core):
  - App móvil: alto (uso familiar; el objetivo es frenar abuso, no al usuario).
  - Terceros con API key: bajo (por key); la respuesta de exceso usa el envelope del ADR 0007 con `code: rate_limited` y HTTP 429.
- El detalle de umbrales y ventanas se fija en el plan del Core; aquí queda el requisito y el mecanismo.

### 3.4 CORS (C2)

- **Allowlist por instancia** en `settings` — clave `connectivity.cors_allowlist` (config del instalador, ADR 0008; ver spec de datos del Core `2026-10-26-core-data-model.md` §3.3). Default: same-origin (el admin consume su propia API) + los orígenes que quien instala añada.
- El móvil no aplica CORS (no es navegador). Sin allowlist configurada, se rechazan orígenes no listados (sin `*` por defecto).

### 3.5 Formato de errores (D1)

- Envelope del **ADR 0007** como formato HTTP de error:

  ```json
  { "error": { "code": "validation_failed", "message": "...", "request_id": "...", "details": [ ... ] } }
  ```

- Mapeo HTTP mínimo: 400 (forma), 401, 403, 404, 409, 429, 500. Sin internos (SQL/stack/rutas/secrets) jamás, ni en dev; `request_id` para correlación con logs.
- RFC 9457 (Problem Details) queda descartado por ahora; la spec puede reabrirlo si la superficie pública de terceros lo justifica (nota, no decisión).

### 3.6 Paginación (D2)

- **Ambos desde v1**:
  - **Offset-limit** (default): `?offset=0&limit=50` (limit con tope máximo), respuesta con `{ data, meta: { total, offset, limit } }`.
  - **Cursor** para listados que lo necesiten: `?cursor=<opaco>&limit=50`, respuesta con `{ data, meta: { next_cursor } }`. Los recursos candidatos (listados grandes o en vivo) lo declaran en su spec de módulo.
- Los IDs son UUID (spec §8): el cursor nunca expone orden interno.

### 3.7 Fechas y moneda (D3)

- ADR 0008: instantes ISO 8601 UTC (`Z`), fechas de calendario como `date` (`YYYY-MM-DD`), `amount_minor` (entero) + `currency` (ISO 4217) en todos los recursos con dinero. El servidor **no formatea**; el cliente lo hace con el locale (config de instancia).
- Validados con zod en el borde (ADR 0004 §3).

### 3.8 MCP (E)

- **Mismo backbone**: las herramientas MCP llaman a los **mismos casos de uso** y devuelven la **misma representación compartida** que el REST (ADR 0004 §7). No hay contrato MCP separado: la tool declara la acción expuesta y sus scopes; el guard autoriza igual.
- **Autenticación**: **API key de instancia** (`027_svc_`, spec de tokens §3.2 — sin identidad de usuario, scopes por módulo; no existe un tipo `mcp` en la taxonomía de tokens). Transporte: endpoint HTTP del MCP (spec §7).
- **Alcance v1**: herramientas del primer módulo (Split Expenses) + lectura básica de **categorías y sus usuarios** (*corrección 2026-10-26:* "grupos/miembros" = categorías de usuarios del Core; los grupos de los módulos no son superficie transversal). Se amplía con cada módulo; el detalle de tools vive en la spec de cada módulo.
- **Delta 2026-10-26 (topología y acciones)**: el MCP deja de ser un endpoint único y de solo lectura. Se expone **un endpoint por módulo** (`/mcp/<module_key>`) más dos generales del Core (`/mcp` usuario, `/mcp/admin` administración), con **acciones** además de consultas (invitar, gestionar usuarios/categorías, conceder acceso a módulos, settings no secretos) y escrituras en las tools de módulo. Detalle completo en `2026-10-26-mcp.md`; fuera de MCP quedan el ciclo de vida de módulos, las API keys y los settings secretos.

### 3.9 Eventos realtime (F)

- Contrato de eventos (ADR 0006): formato `{ type, resource, payload }`:  - `type`: `snake_case` del evento de dominio (p. ej. `expense.created`).
  - `resource`: la **representación compartida** del recurso afectado (mismo shape que su endpoint REST).
  - `payload`: datos adicionales no sensibles que el evento necesita.
- Suscripción por topic de grupo (`group-<id>`, `private: true`, RLS sobre `realtime.messages`). **Desviación registrada del ADR 0006:** el 0006 esperaba que esta spec fijara el contrato completo de eventos (nombres y payloads por recurso); aquí se fija el **envelope** y se difieren nombres/payloads por recurso a la spec de cada módulo — coherente con la decisión G (el Core no se cataloga aquí). Los payloads de eventos del Core (del mínimo de arranque) se listan con los recursos cuando el sprint de diseño del Core los defina.
- **Delta 2026-10-26 (topología y enrutado):** la topología "topic por grupo" queda **sustituida por el [ADR 0009](../../adr/0009-topologia-de-canales-realtime.md)** (canales con destinatario explícito: `admins`, `all`, `user-<uuid>` y canales de módulo). El **envelope del wire no cambia** (`{ type, resource, payload }`); el servidor añade `target`/`subject` como **metadato interno de enrutado** que no viaja al cliente. Los payloads de los eventos del Core están catalogados en `2026-10-26-realtime-notificaciones.md` §4.

## 4. Mínimo transversal de arranque

Endpoints que el contrato y el arranque necesitan hoy (el resto de la superficie del Core se decide en el sprint de diseño del Core):

| Endpoint | Público | Qué devuelve |
|---|---|---|
| `GET /api/v1/health` | Sí | `{ status: "ok" \| "degraded" }` (sin auth; si falla Supabase → degraded) |
| `GET /api/v1/instance` | Sí (metadatos **no sensibles**) | versión, nombre de instancia, locales activos, moneda/zona por defecto, `requires_setup` (wizard pendiente), `status`. **Trade-off aceptado:** `requires_setup` es público, revela "instancia sin admin" a quien explore la URL. Es acotado y coherente con el diseño del wizard de instalación (auth spec §3bis): la ventana de setup es pública por definición y desaparece al existir el primer admin; no expone datos ni secrets. |
| `GET /api/v1/modules` | Con auth | catálogo de módulos de la instancia: id, estado del registry (`installed`/`disabled`), versión |
| `GET /api/v1/me/modules` | Con auth | módulos a los que **el llamador tiene acceso** (`user_modules`) y su estado. **Sustituye al anterior `GET /api/v1/groups/{id}/modules`** (corrección 2026-10-26: el acceso es por usuario, no por grupo/categoría) |

Estos devuelven la representación compartida y siguen el contrato (errores, paginación si aplica). Son la semilla: el **sprint de diseño del Core** concreta el resto (categorías y sus usuarios, invitaciones, api-keys, device-tokens, etc.) sobre esta base.

**Corrección (2026-10-26, sprint de diseño del Core):** con el reframe del Core (las **categorías** son etiquetas de usuarios; los **grupos** reales los modela cada módulo con sus propias tablas), el endpoint `GET /api/v1/groups/{id}/modules` **se sustituye por `GET /api/v1/me/modules`**: el acceso a módulos es **por usuario** (`user_modules`), nunca por categoría, y la **config específica de módulo** (p. ej. la moneda de Split Expenses) **no es transversal** — es recurso propio de cada módulo. La superficie transversal declarada queda en `/health`, `/instance`, `/modules`, `/me/modules` y la lectura de categorías/usuarios en MCP (matiz a la decisión G).

**Nota sobre el límite de alcance (G):** estos endpoints y la lectura de categorías/usuarios de MCP son la **única** superficie transversal declarada aquí — lo que el contrato y el arranque exigen; todo lo demás lo decide el sprint de diseño del Core (matiz a la decisión G).

## 5. Mecanismo de extensión

Cómo el Core y cada módulo añaden recursos al contrato **sin tocar su mecánica**:

1. **Schemas zod compartidos** en `packages/*` (source of truth del contrato: entrada + recurso de salida).
2. **Caso de uso orquestador** con nombre (ADR 0004 §4): el módulo compone sus acciones como casos de uso con nombre; la puerta solo autentica/autoriza/valida.
3. **Representación compartida**: el recurso de salida se produce en la capa de serialización compartida; la misma forma sirve a REST, MCP y eventos.
4. **OpenAPI regenerado** desde los schemas (el CI verifica que el contrato generado está al día).
5. **La puerta declara sus scopes** por acción expuesta; el guard los comprueba con el resto (nada nuevo que inventar).

El resultado: añadir un módulo = añadir schemas + casos de uso + recursos + la declaración de scopes, y el contrato se regenera. La mecánica (versionado, errores, paginación, rate limiting, CORS, MCP, eventos) **no cambia jamás por un módulo**.

## 6. Fuera de alcance

- **Inventario completo de endpoints del Core** → sprint de diseño del Core (sobre este contrato).
- **Endpoints de módulos** (Split Expenses: expenses, balances, splits; etc.) → spec de cada módulo.
- **Detalle de umbrales de rate limiting** → plan del Core.
- **MCP tools concretas** → spec de cada módulo.
- **Implementación** → Core (bloqueada hasta que esta spec y las del Core estén `finalizada`).

## 7. Criterios de aceptación

- La API v1 expone `/health`, `/instance`, `/modules`, `/me/modules` (corrección 2026-10-26: sustituye a `GET /api/v1/groups/{id}/modules`) con el contrato de esta spec; el resto lo añade el sprint del Core **sin tocar la mecánica** (mecanismo de extensión verificado por el test de puerta: un módulo nuevo solo añade schemas/casos de uso/recursos).
- El OpenAPI se genera desde los schemas zod compartidos y el CI verifica que está al día.
- Toda respuesta de error usa el envelope del ADR 0007 (sin internos, con `request_id`).
- La paginación offset-limit y cursor funcionan sobre cualquier listado declarado.
- MCP llama a los mismos casos de uso que REST y devuelve la misma representación.
- Los eventos realtime usan `{ type, resource, payload }` con la representación compartida.
- El guard-central autoriza por scopes por acción expuesta (móvil JWT, terceros API key, MCP con clave de instancia `027_svc_` — sin tipo `mcp`).

## 8. Decisiones tomadas (conversación de diseño, 2026-10-25)

| # | Decisión |
|---|---|
| A1 | `/api/v1` fijo en URL; cambios incompatibles → nueva versión |
| A2 | OpenAPI **generado** desde schemas zod compartidos (source of truth) |
| B1–B3 | API keys opacas con scopes (expiración/rotación/revocación, spec de tokens); móvil con JWT Supabase; acceso efectivo `min(scopes, permisos)`; permisos en vivo |
| C1 | Rate limiting por identidad en código, umbrales diferenciados (móvil alto / terceros bajo); exceso → 429 + envelope |
| C2 | CORS allowlist por instancia en `settings` (`connectivity.cors_allowlist`); default same-origin; sin `*` por defecto |
| D1 | Envelope del ADR 0007 como formato HTTP de error; RFC 9457 descartado (reabrible) |
| D2 | Offset-limit (default) + cursor, ambos en v1 |
| D3 | ADR 0008: ISO 8601 UTC, `date`, `amount_minor` + `currency`; servidor no formatea |
| E1–E2 | MCP sobre el mismo backbone (mismos casos de uso + representación); tools v1 = Split Expenses + lectura de categorías/usuarios (corrección 2026-10-26); clave de instancia `027_svc_` (sin tipo `mcp` — alinea §3.8) |
| F | Eventos `{ type, resource, payload }`, resource = representación REST, topic por grupo (ADR 0006) |
| G | El inventario del Core NO se cierra aquí: lo define el sprint de diseño del Core; esta spec fija el contrato + mínimo de arranque (`/health`, `/instance`, `/modules`, `/me/modules` — corrección 2026-10-26, sustituye a `/groups/{id}/modules` — los 4 únicos transversales declarados) + mecanismo de extensión |
