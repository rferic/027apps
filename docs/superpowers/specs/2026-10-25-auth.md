# Spec — Autenticación (sprint 03, task 04)

**Fecha:** 2026-10-25
**Estado:** Borrador para aprobación del usuario
**Base:** spec de tokens `2026-10-25-token-model.md` (revisada) · [ADR 0004](0004-bordes-y-capa-de-aplicacion.md) · [ADR 0005](0005-estado-y-fetching-del-admin.md) · spec de diseño §2/§4/§6/§11
**Decide el usuario:** frontera Supabase vs propio; método de autenticación del móvil (2026-10-25)

## 1. Objetivo

Definir cómo una **persona** (miembro de la familia) obtiene identidad en 027Apps, cómo se empareja cada dispositivo, cómo se recupera una sesión perdida, cómo se autentica el admin web, y **la frontera exacta** entre lo que gestiona Supabase y lo que montamos nosotros.

## 2. Frontera decidida (2026-10-25)

> **Supabase = identidad y transporte.** **Nosotros = autorización, invitación, casos de uso, tokens de máquina y eventos de dominio.**

| Pieza | Responsable |
|---|---|
| Identidad móvil (GoTrue): email+contraseña, sesión con refresh rotativo, reset de contraseña, rate limiting del login | **Supabase** |
| Transporte realtime (WebSocket, entrega, mensajes; cliente Kotlin `supabase-kt`) | **Supabase** |
| Invitación (URL de un solo uso, email + módulos, wizard) | **Nosotros** |
| Autorización en `/api/v1` (guard `authorize(caller, scopes)`, scopes por acción expuesta) | **Nosotros** |
| Tokens de máquina: instancia (`027_svc_…`) y delegado (`027_usr_…`), opacos + BD | **Nosotros** (sin cambio respecto a la spec de tokens) |
| Casos de uso + zod en el borde + representación compartida (ADR 0004) | **Nosotros** |
| RLS por grupo (datos y membresía de canales realtime) | **Nosotros** (mecanismo de Supabase) |

## 3. Alta: la invitación es el único vehículo

1. El admin genera una **invitación** (URL, token de un solo uso, email + módulos/grupo; tabla `invitations`). Cómo se distribuye (WhatsApp, email…) queda como detalle de UX. **Un grupo por invitación** (coherente con `invitations.group_id`).
2. Al abrir la URL sale el **wizard**:
   - Si la app no está instalada: **QR de descarga del APK**.
   - Si está instalada: **deep-link** ("Abrir en la aplicación") como camino principal; **QR + código** como alternativa para emparejamiento cruzado desde otra pantalla.
3. **Confirmar email + fijar contraseña: se hace en la app**, no en el navegador. El navegador solo recibe el enlace de invitación (y el deep-link/QR solo transporta el **token de invitación**, nunca credenciales ni sesión). Tras el hand-off, la app muestra los campos de email + contraseña, llama a nuestro caso de uso de canjeo, y **firma en Supabase Auth** con esas credenciales. El navegador nunca ve la contraseña y no se transfiere sesión por el canal de emparejamiento (la transferencia móvil→móvil sigue aplazada).
4. Al completar, **nosotros** creamos (o verificamos) el usuario en **Supabase Auth** vía Admin API con ese email, activamos la afiliación (grupo + módulos de la invitación), y la app guarda la sesión en su almacén seguro.
5. Casos límite: email ya existente → flujo de unión (login con contraseña contra la invitación); **invitación caducada → `invitation_expired`** y **ya usada → `invitation_used`** (códigos de dominio, ADR 0007; ambos HTTP 409); email de la invitación ≠ email confirmado → no procede.

## 3bis. Bootstrap: primer super_admin (wizard de instalación)

Los usuarios **solo** se registran por invitación. Los administradores se crean desde la **página de administración**. El **primer super_admin** se crea con un **wizard de instalación** que la web muestra cuando detecta que no existe ningún admin y se cumplen las verificaciones correspondientes (estilo WordPress):

- La web, sin ningún admin en la instancia, redirige a `/setup` con un **wizard de instalación** que agrupa los pasos iniciales uno-tras-otro (los concretos se definen en el sprint de infra): **1) conexión con Supabase** (proyecto + envs), **2) SMTP del proyecto** (proveedor gratuito Resend/Brevo o el que elija quien instala) y **3) creación del super_admin** (email + contraseña).
- Crea el primer usuario en Supabase Auth (vía Admin API) y lo marca `super_admin` en `profiles`.
- Una vez creado, el wizard desaparece (la comprobación "existe al menos un admin" lo apaga) y rige la invitación para todo lo demás.
- **Seguridad:** el wizard solo existe si no hay ningún admin — que lo intente quien tenga acceso a la URL de la instancia mientras tanto. Se anota en la auditoría: la ventana de instalación es el único momento de alta sin invitación, y desaparece con el primer admin.

## 4. Sesión del móvil

- **Supabase Auth:** access + refresh con **rotación**; la app los persiste solo en el almacén seguro del dispositivo (Android Keystore / EncryptedSharedPreferences).
- **"Login una vez":** en uso normal el usuario no vuelve a interactuar; la app refresca en segundo plano.
- **Llamadas a `/api/v1`:** `Authorization: Bearer <JWT de Supabase>`. Nuestra API **verifica el JWT** (identifica al usuario), y el **guard resuelve scopes/membresía** contra la BD (ADR 0004). Supabase emite la identidad; nosotros autorizamos cada petición.
- **Revocación:** sesión de Supabase revocable por dispositivo; un miembro expulsado del grupo pierde el acceso de datos **al instante en cada petición nueva** (RLS + guard). La revocación de una **conexión realtime abierta** queda acotada a la vida del access token: para cumplir el criterio de "~15 min" el proyecto se configura con `JWT_EXPIRY = 900 s` (no es el default de 3600 s; se define en la instalación) — lag acotado y documentado.

## 5. Recuperación

- **Móvil perdido:** login con **email + contraseña** en el dispositivo nuevo → se crea una sesión nueva. La contraseña, fijada en el emparejamiento inicial, es la credencial de recuperación.
- **Contraseña olvidada:** **reset por email** gestionado por Supabase Auth.
- El admin puede **revocar sesiones** de un dispositivo desde el panel.

## 5bis. Envío de emails (gratis)

Los emails de auth (confirmación y, sobre todo, **reset de contraseña**) los envía **Supabase Auth**, no nuestra app. El servicio de email por defecto de Supabase está limitado a **2 emails/hora (best-effort, solo pruebas)**, así que para producción se configura un **custom SMTP**, **incluido en el plan Free**.

- Cada instancia conecta su propio SMTP en el **proyecto Supabase** (dashboard, durante la instalación; puerta de usuario): un **proveedor gratuito** a elegir por quien instala — **Resend** (3.000/mes, 100/día) o **Brevo** (300/día) cubren con enorme margen el volumen familiar (resets ocasionales).
- **Distinción de dos SMTP distintos (esto es «el tema del SMTP» a decidir en el sprint de infra):**
  - **SMTP para Supabase Auth** (reset de contraseña, confirmación): configuración del **proyecto Supabase** (nunca en `settings`).
  - **SMTP/API key para emails propios de nuestra app** (si un día enviamos enlaces de invitación por email u otros mensajes): esto **sí** va cifrado en `settings.value_encrypted` (clave maestra en env; ver `2026-10-26-instance-config.md`), que es lo que prevé la spec de diseño §8 con "SMTP, futuras LLM keys BYOK, secrets de clientes MCP". Hoy no hay emails propios; el sitio queda reservado.
- **Decisión pendiente (backlog, sprint de infra, puerta de usuario):** elegir el proveedor concreto (Resend vs Brevo), confirmar si el proyecto envía algún email propio además del reset, y el comportamiento en dev/preview (Mailpit en local; modo test en un proyecto Supabase de preview).

## 6. Admin web

- Mismo **Supabase Auth** (email + contraseña), sesión server-side desde Next (helper SSR de Supabase).
- Roles: `super_admin` (instancia) y `admin` de grupo, desde `profiles` + `group_members`; RLS + guard en el panel.

## 7. Realtime: Broadcast con eventos de dominio publicados por la API

- **Nuestra API publica eventos de dominio tras el commit** de cada caso de uso (ADR 0004 §6: efectos externos fuera de la transacción) al **topic del grupo** (`group-<id>`).
- El móvil se suscribe con su sesión; la **membresía del canal** se protege con **RLS sobre `realtime.messages`** (topic por grupo, `private: true`) — Supabase valida quién puede unirse, nosotros escribimos esa política. **El amigo X no puede unirse al topic del grupo de mi pareja.**
- **El payload del evento usa la representación compartida** (ADR 0004 §7): mismo recurso que su endpoint REST. (La publicación concreta servidor→Realtime — broadcast vía service-role o tabla de eventos + suscripción — la decide el plan, verificándolo contra la doc vigente de Supabase.)
- **Tokens de máquina:** el de **instancia** no se suscribe por defecto (sin sujeto/membresía); el **delegado sí tiene sujeto** (actúa como un usuario, spec de tokens §3.3), pero en v1 tampoco se suscribe — si un caso lo justifica, la spec de API v1 define el mecanismo explícito.

## 8. Consecuencia sobre la spec de tokens

La spec `2026-10-25-token-model.md` **queda revisada en §3.1**: el "token de dispositivo" opaco **desaparece**; la autenticación del móvil es **sesión de Supabase Auth**. Los tokens opacos quedan para **instancia y delegado**. Esta spec fija esa revisión; la spec de tokens se ajusta en consecuencia.

## 9. Fuera de alcance

- **API pública v1** (OpenAPI, versionado, rate limiting de terceros) → spec siguiente, que referencia esta frontera.
- **MCP** → spec de API v1.
- **i18n** de los textos del wizard → flujo i18n.
- **Transferencia móvil → móvil** → aplazada (diseño posible, implementación futura).

## 10. Criterios de aceptación

- Alta de usuarios **solo** por invitación (confirmar email + fijar contraseña en la app); invitación de un solo uso. Única excepción: el **primer super_admin vía wizard de instalación** (§3bis), que desaparece al existir un admin.
- El móvil "entra una vez" y no vuelve a pedir credenciales en uso normal; recuperación por email + contraseña en un dispositivo nuevo; reset de contraseña por email (Supabase + custom SMTP, §5bis).
- `/api/v1` verifica el JWT de Supabase e identifica al usuario; el guard autoriza por scopes/membresía en cada petición.
- Los eventos realtime llegan **solo** a los miembros del grupo (X no ve lo de Y), con representación compartida y publicación tras el commit; la vida del access token (15 min) acota la revocación de conexiones abiertas.
- El admin web autentica con Supabase Auth y respeta roles (super_admin / admin de grupo).
- La spec de tokens queda ajustada (sin "token de dispositivo" opaco; sesión Supabase en su lugar).
