**Estado:** Borrador para aprobación del usuario

**Decide el usuario:** inventario de endpoints, scopes por rol, rate limiting C1, filtros de listados (2026-10-26)

## 1. Objetivo

Definir el **inventario de endpoints transversales del Core** sobre el contrato estable de API v1 — la superficie única de datos para móvil, admin y terceros (API-first, ADR 0004) —, sus **scopes por acción expuesta** (incluido el modelo de 3 roles `super_admin`/`admin`/`user`), los **filtros** de los listados y el **rate limiting** (decisión C1 delegada por api-v1 §3.3). Cada endpoint es una **puerta delgada** que autentica, autoriza (guard `authorize(caller, scopes)`), valida (zod) y delega en el caso de uso; devuelve la **representación compartida** (ADR 0004 §7).

**Límite de alcance:** aquí se fijan los recursos y contratos de los endpoints del Core. Los **endpoints de los módulos** (p. ej. `expenses` de Split Expenses) son de la spec de cada módulo. Los **jobs/observabilidad** de mantenimiento de algunos recursos (`audit`, cierre de ventanas) van en task-07/08; el **catálogo de settings** y el wizard en task-06; el **instalador de módulos** en task-03.

## 2. Roles y scopes (qué significa "autorizado")

Del modelo de datos (task-01, decisiones M/N):

| Rol | Alcance |
|---|---|
| `super_admin` | Todo: gestión de la instancia + gestión de `super_admin` (promocionar/demotar/borrar salvo el root) + acceso a **todos los módulos** |
| `admin` | Gestión de la instancia (usuarios, categorías, invitaciones, módulos, settings, api-keys, traducciones) + **crear/actualizar admins** (no super_admins) + acceso a **todos los módulos** |
| `user` | Sus datos: perfil propio, sus `user_modules`, módulos **públicos** (`is_public`) |

**Scopes por acción expuesta** (ADR 0004 §2, spec de tokens §5): cada puerta declara los scopes que exige; el guard los comprueba. Convención de nombres: `recurso:acción` (`users:read`, `users:write`, `roles:assign`, `modules:manage`, `settings:write`…). Para una clave delegada el acceso efectivo es `min(scopes de la clave, permisos del usuario)`; para una clave `service`, los scopes de la clave; para el móvil/admin, los del rol (task-01 §4).

**Regla de rol en los endpoints de gestión:** salvo los marcados como "propietario", los endpoints de gestión requieren `is_admin()` (super_admin **o** admin). Los que gestionan roles de `super_admin`, el root, `module_migrations` y `audit`/`admin_actions` requieren `is_super_admin()`.

## 3. Inventario de endpoints

### 3.1 Identidad y perfil

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/me` | mi perfil | `profile:read` | el propio usuario |
| `PATCH /api/v1/me` | editar `display_name`, `locale`, `timezone` | `profile:write` | el propio usuario (**no** `role`) |
| `GET /api/v1/me/modules` | mis módulos (públicos + `user_modules` activos) + estado | — (derivado) | el propio usuario |

### 3.2 Usuarios

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/users` | listar usuarios | `users:read` | `is_admin()` |
| `GET /api/v1/users/{id}` | detalle de usuario | `users:read` | `is_admin()` |
| `PATCH /api/v1/users/{id}` | editar `display_name`, `locale`, `timezone`, **`role`** | `users:write` + `roles:assign` (para `role`) | `is_admin()`; **solo `is_super_admin()`** promociona/demota `super_admin`; el **root** (`/setup`) no se demota ni borra |

**Filtros de `GET /users`** (decisión usuario, 2026-10-26):
- `q` — búsqueda por nombre/email (selectores)
- `module=<key>` — solo usuarios con acceso a ese módulo (para "añadir usuarios a un grupo de módulo": cruza `user_modules` + `is_public` + admins)
- `category=<id>` — miembros de una categoría
- Paginación offset/cursor del contrato v1 (D2).

### 3.3 Categorías de usuarios

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/user-categories` | listar categorías | `user_categories:read` | `is_admin()` |
| `POST /api/v1/user-categories` | crear | `user_categories:write` | `is_admin()` |
| `GET /api/v1/user-categories/{id}` | detalle + miembros | `user_categories:read` | `is_admin()` |
| `PATCH /api/v1/user-categories/{id}` | renombrar | `user_categories:write` | `is_admin()` |
| `DELETE /api/v1/user-categories/{id}` | borrar (no revoca concesiones materializadas) | `user_categories:write` | `is_admin()` |
| `POST/DELETE /api/v1/user-categories/{id}/members/{userId}` | añadir/quitar miembro | `user_categories:write` | `is_admin()` |
| `GET /api/v1/user-categories/{id}/modules` | módulos de la categoría | `user_categories:read` + `modules:read` | `is_admin()` |
| `POST/DELETE /api/v1/user-categories/{id}/modules/{key}` | **asignar/quitar módulo a la categoría** (**materializa** `user_modules` a los miembros actuales — decisión A2) | `user_categories:write` + `modules:grant` | `is_admin()` |

### 3.4 Módulos (catálogo y gestión)

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/modules` | catálogo de la instancia: key, name, version, `state`, **`is_public`** | `modules:read` | cualquier autenticado |
| `GET /api/v1/modules/{key}` | **detalle**: estado + versión + `is_public` + **sus settings** (de `settings_categories` con `source: module:<key>`) | `modules:read` | autenticado con `has_module_access(key)` o `is_admin()` |
| `GET /api/v1/modules/{key}/settings` | leer config del módulo | `modules:read` + `settings:read` | `is_admin()` |
| `PATCH /api/v1/modules/{key}/settings` | actualizar config del módulo | `modules:manage` + `settings:write` | `is_admin()` |
| `POST /api/v1/modules/{key}/install` · `/activate` · `/deactivate` | ciclo de vida (mecánica en task-03) | `modules:manage` | `is_admin()` |
| `POST /api/v1/modules/{key}/uninstall` | desinstalar (reversión de migraciones; exige confirmación si hay concesiones/settings en uso) | `modules:manage` | `is_super_admin()` |
| `PATCH /api/v1/modules/{key}` | cambiar `is_public` (override del manifest) | `modules:manage` | `is_admin()` |
| `POST /api/v1/users/{id}/modules/{key}` | **conceder** acceso a un usuario | `modules:grant` | `is_admin()` |
| `DELETE /api/v1/users/{id}/modules/{key}` | **revocar** (soft, `revoked_at`; re-grant lo restablece) | `modules:grant` | `is_admin()` |

### 3.5 Invitaciones (alta)

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `POST /api/v1/invitations` | crear (email, nombre, `user_category_id`, módulos a conceder) | `invitations:write` | `is_admin()` |
| `GET /api/v1/invitations` | listar (con estado pendiente/usada/caducada) | `invitations:read` | `is_admin()` |
| `DELETE /api/v1/invitations/{id}` | revocar | `invitations:write` | `is_admin()` |
| `POST /api/v1/invitations/{token}/redeem` | **canjeo del wizard** (crea/verifica `profiles`, `user_category_members`, materializa `user_modules` de `invitation_modules`) | — (público con token de un solo uso) | el invitado |

### 3.6 Tokens de máquina

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `POST /api/v1/api-keys` | crear clave (service o delegada) | `api_keys:write` | service → `is_super_admin()`; delegado → el propio usuario |
| `GET /api/v1/api-keys` | listar mis claves (delegadas) / todas (service, super_admin) | `api_keys:read` | propietario / `is_super_admin()` |
| `GET /api/v1/api-keys/{id}` | detalle + uso (`audit` agregado) | `api_keys:read` + `audit:read` | propietario (delegado) / `is_super_admin()` |
| `DELETE /api/v1/api-keys/{id}` | revocar (instantánea) | `api_keys:revoke` | service → `is_super_admin()`; delegado → propietario |

> El secreto completo de una clave **solo** se muestra una vez al crear (spec de tokens §6); los listados devuelven prefijo + `last_used_at`, nunca el secreto.

### 3.7 Dispositivos

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/devices` | mis dispositivos | `devices:read` | el propio usuario |
| `GET /api/v1/devices?user={id}` | dispositivos de un usuario (panel) | `devices:read` | `is_admin()` |
| `DELETE /api/v1/devices/{id}` | revocar dispositivo (soft + Admin API de Supabase) | `devices:revoke` | propietario / `is_admin()` |

### 3.8 Configuración e instancia

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/instance` | metadatos no sensibles (versión, nombre, locales activos, moneda default, `requires_setup`, `status`) | — (público) | cualquiera |
| `GET /api/v1/settings` | leer settings (solo no sensibles si no eres admin) | `settings:read` | `is_admin()` (todo) / propietario (solo no sensibles vía filtro) |
| `PATCH /api/v1/settings/{category}.{key}` | escribir settings (`value` o `value_encrypted` según `is_secret`; validación zod del catálogo, task-06) | `settings:write` | `is_admin()` |
| `GET /api/v1/settings-categories` | categorías de settings (para el panel, agrupadas por `sort_order`) | `settings:read` | `is_admin()` |
| `GET /api/v1/currencies` | monedas habilitadas | `currencies:read` | autenticado |
| `PATCH /api/v1/currencies/{code}` | habilitar/deshabilitar (la default no se desactiva) | `currencies:write` | `is_admin()` |

### 3.9 Traducciones (kernel i18n)

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/translations?locale={l}` | **resolución i18n en runtime**: pares `text_en → translated_text` para el locale (o fallback `en`) | — (autenticado) | cualquier autenticado |
| `GET /api/v1/translations/status` | cobertura por locale (% traducido, faltantes) | `translations:read` | `is_admin()` |
| `POST /api/v1/translations/import` | importar traducciones (por `text_hash`) | `translations:write` | `is_admin()` |
| `PUT /api/v1/translations/{locale}/{text_hash}` | actualizar/crear traducción | `translations:write` | `is_admin()` |

> La **pipeline** (generación de claves, sync, check de CI) y el detalle de cobertura van en task-09; aquí el contrato del recurso. El kernel `resolve(text_en, locale) = translations(locale, hash) ?? translations(en) ?? text_en` (task-01 §3.3).

### 3.10 Administración y salud

| Método y ruta | Acción | Scopes | Quién |
|---|---|---|---|
| `GET /api/v1/health` | `{ status: ok \| degraded }` | — (público) | cualquiera |
| `GET /api/v1/admin-actions` | log de mutaciones sensibles (paginado) | `admin:read` | `is_super_admin()` |
| `GET /api/v1/audit` | uso agregado de tokens (ventanas) | `audit:read` | `is_super_admin()` |

## 4. Rate limiting (decisión C1)

La spec de API v1 §3.3 delega el detalle "al plan del Core": aquí se fija.

- **Mecanismo**: por **identidad** (token/usuario), en **código en la puerta**, con **ventana deslizante**. En v1 el contador vive en **memoria/Redis del deploy** (Vercel free no expone IP-limits de plataforma); si el contador necesita persistencia multi-instancia, se evaluará una tabla de contadores (puente a task-07).
- **Umbrales iniciales** (valores de arranque a calibrar en el primer módulo real):
  - **Móvil/admin (sesión Supabase)**: alto — p. ej. **120 req/min** por usuario.
  - **Terceros (API key)**: bajo — p. ej. **30 req/min** por key.
  - **MCP (clave service)**: p. ej. **30 req/min** por clave.
  - Los endpoints públicos (`/health`, `/instance`, `/invitations/{token}/redeem`) tienen su propio límite acotado (p. ej. 30 req/min por IP/token) para no abrir superficie de abuso.
- **Exceso**: HTTP **429** + envelope del ADR 0007 con `code: rate_limited`, `message` por defecto y `retry_after` en los headers.
- **Config**: los umbrales viven como settings (`security.rate_limit.*`) para ajuste por instancia (task-06).

## 5. Representaciones (recursos)

Cada recurso usa la **representación compartida** (ADR 0004 §7), producida por la capa de serialización común a REST/MCP/eventos. Reglas del contrato v1: errores envelope (ADR 0007), paginación offset/cursor (D2), fechas ISO 8601 UTC / `date` / `amount_minor` (ADR 0008), servidor no localiza (el texto de `translations` se resuelve en cliente con el kernel).

Representaciones mínimas (a detallar con zod en la implementación):
- `User` — id, display_name, locale, timezone, `role` (admin/super_admin), created_at.
- `UserModule` — module_key, name, state, is_public, granted (bool), revoked_at.
- `UserCategory` — id, name, slug, member_count, modules[].
- `Module` — key, name, version, state, is_public, settings_url.
- `Invitation` — id, email, name, category, modules[], status (pending|used|expired), expires_at.
- `ApiKey` — id, kind, name, prefix, scopes, created_at, last_used_at, expires_at, revoked_at (**nunca** el secreto).
- `Device`, `Setting` (con `is_secret` para no filtrar `value_encrypted`), `Currency`, `Translation`, `AdminAction`, `Health`.

## 6. Decisiones tomadas (conversación de diseño, 2026-10-26)

| # | Decisión |
|---|---|
| A | **Roles y scopes**: `super_admin`/`admin`/`user` (task-01 M); gestión bajo `is_admin()`, lo de super_admin solo `is_super_admin()`; `roles:assign` para promocionar (admin → admins; super_admin → super_admins; root protegido) |
| B | **Alta solo por invitación** (`/redeem`) + `/setup` para el primer super_admin; sin auto-registro |
| C | **Filtros de listados**: `GET /users` con `q`, `module=<key>`, `category=<id>` + paginación (selectores del admin) |
| D | **Catálogo de módulos**: `GET /modules` (público) + `GET /modules/{key}` (detalle + settings) + settings del módulo vía `/modules/{key}/settings` |
| E | **Módulos público/privado**: `GET /modules` expone `is_public`; `GET /me/modules` = públicos + concesiones + (admins → todos) |
| F | **Rate limiting C1**: por identidad, ventana deslizante, umbrales 120 (móvil) / 30 (key/MCP) req/min, 429 + envelope, configurable por settings |
| G | **Canjeo público**: `POST /invitations/{token}/redeem` sin auth de sesión (token de un solo uso), límite propio |
| H | **Renames**: `user_categories` (recurso `/user-categories`), `settings_categories`, `module_settings` → `/modules/{key}/settings` |

## 7. Fuera de alcance

- **Endpoints de módulos** (expenses, balances, etc.) → spec de cada módulo (Split Expenses la primera).
- **Catálogo concreto de settings** (tipos zod, quién lee cada clave, wizard `/setup`) → task-06.
- **Mecánica del instalador de módulos** (manifest, orden de migraciones, DDL runtime) → task-03.
- **Jobs de auditoría/cierre de ventanas y observabilidad** (Sentry, `request_id`) → task-07/08.
- **Pipeline i18n** (generación, sync, check de CI, skill) → task-09.
- **Checklist OWASP / política de secrets / patrón RLS formalizado** → task-10.
- **Contrato de eventos realtime y notificaciones** → task-04; **MCP tools** → task-05.

## 8. Criterios de aceptación

- El inventario del §3 cubre la superficie transversal del modelo de datos (task-01) sin dejar hueco: identidad, usuarios (con filtros), categorías, módulos (catálogo/detalle/settings/ciclo de vida), invitaciones, api-keys, devices, settings, currencies, translations, admin-actions, health.
- Cada puerta declara sus scopes por acción y el guard los comprueba; los roles `super_admin`/`admin`/`user` se respetan (gestión = `is_admin()`, roles de super_admin/root/audit = `is_super_admin()`).
- El rate limiting queda con mecanismo, umbrales y respuesta `429`+envelope definidos y configurables.
- Los recursos usan la representación compartida y el contrato v1 (errores, paginación, fechas, moneda).
- Coherente con la spec de datos (task-01), la spec de API v1 (con delta), spec de tokens §5, ADR 0004/0007/0008.
- Aprobada por el usuario y revisada por segundo agente (DoD de Docs).
